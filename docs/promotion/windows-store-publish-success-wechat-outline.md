## 第四部分：实施过程（按时间线叙述）
- 阶段 1：工程侧改造（双轨制打包）
  - 保持原有 `.zip` / Inno Setup 独立分发不变
  - 引入 `DistroNexus.Package.wapproj` (Windows Application Packaging Project)
  - 修改 `tools/build.ps1` 支持 `-StoreBuild` 参数，输出 `.msixbundle` (x64 + ARM64 双架构)
- 阶段 2：Partner Center 提交配置
  - 基础信息：定价（免费）、市场、类别（开发者工具）
  - 身份绑定：Package Family Name (PFN) 与证书自动签名机制
- 阶段 3：测试与验证
  - 本地 Sideloading (旁加载) 测试
  - Windows App Certification Kit (WACK) 预检
- 阶段 4：提交审核与发布

## 第五部分：认证审核中的关键难点（硬核干货）
- **最大卡点：`runFullTrust` 权限申请**
  - 为什么需要：DistroNexus 需要调用底层 PowerShell 和 WSL 进程，必须突破 UWP 沙箱。
  - 怎么通过：在提交选项中提供详尽的业务合理性说明（Justification），并附带测试步骤和 WSL 前置环境要求，降低审核员的理解门槛。

## 第六部分：踩坑复盘（真实血泪史）
- **坑点 1：MSIX 运行时的路径陷阱**
  - 问题：商店应用安装在只读的 `C:\Program Files\WindowsApps\`，导致部分相对路径写入失败。
  - 解决：利用 Desktop Bridge 特性，将日志和配置重定向到真实的 `AppData` 目录。
- **坑点 2：版本号的“潜规则”**
  - 问题：商店要求四位版本号（如 `2.0.1.0`），且第四位必须保留为 `0` 供商店系统使用。
  - 解决：调整 CI/CD 脚本，严格遵守 `Major.Minor.Patch.0` 规范，每次重新提交只递增前三位。
- **坑点 3：视觉资产的严苛要求**
  - 问题：商店对 Logo 尺寸（如 300x300 磁贴、44x44 任务栏图标）和截图比例有严格限制。
  - 解决：提前准备好全套标准尺寸素材，避免在 Partner Center 提交流程中反复返工。
