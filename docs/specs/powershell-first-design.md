## Architecture and Ownership

The public flow is `PowerShell caller or WPF -> PowerShell module -> capability adapter -> WorkspaceBridge/Core or approved native command -> typed result`. The WPF client accesses this flow through a closed, typed `IPowerShellModuleClient` abstraction. It cannot submit arbitrary PowerShell text, arbitrary bridge operation names, or raw process arguments. The client operation registry is compiled from supported cmdlet families and serializes only validated typed parameters.

`src/PowerShell` owns public command names, parameter grammar, `ShouldProcess`, output/error envelopes, and the decision whether a command needs bridge support. `src/Client/DistroNexus.WorkspaceBridge` owns only internal versioned capability operations and invokes Core services. `src/Client/DistroNexus.Core` owns domain models, validation helpers, safe persistence and platform adapters. `src/Client/DistroNexus.Desktop` owns binding, dialogs, navigation, rendering, and an explicitly narrow external-presentation adapter. It must not reference Core business service interfaces after the relevant migration slice.

The migration uses these ordered capability families: (1) module-contract integrity and boundary guard; (2) instance lifecycle, catalog/source/cache, backup, tags, settings; (3) WSL and distribution configuration; (4) templates, marketplace, and workspace; (5) network, systemd, firewall; (6) recovery, health, diagnostics; (7) WSLg, containers, Docker; (8) monitoring, USB, platform/update/terminal; (9) WPF consumers; (10) closure evidence. A family is not complete until its exported commands, bridge/internal route, WPF consumers, tests, and inventory rows agree.

## Contracts and Behavior

- Contracts: Each command family declares command names, typed parameters, result schema, mutation classification, and bridge requirement in the capability inventory. Bridge requests use an operation identifier selected by the module, a versioned JSON request body, cancellation correlation, and a typed JSON response/error envelope. Desktop uses the corresponding typed client method rather than command text. The initial closed `IPowerShellModuleClient` registry exposes only `GetInstanceTagsAsync`; it maps to `Get-DistroNexusInstanceTag` and accepts only an optional instance name and cancellation token. It deliberately has no text/script, cmdlet-name, bridge-operation, or raw-argument input.
- Validation: Public PowerShell parameters reject missing, malformed, unsafe, or unsupported input before bridge invocation. Core repeats security-critical validation. Desktop validates only presentation affordances and relies on the returned validation error as authoritative.
- Authorization and scope: All mutations use `[CmdletBinding(SupportsShouldProcess)]` and `ShouldProcess`; `WhatIf` and declined confirmation prevent internal execution. Existing preview tokens, fingerprints, elevation grants, and trusted executable checks remain mandatory and are passed only through typed fields.
- Errors and compatibility: Preserve existing successful output fields where feasible. New commands emit stable objects rather than formatted strings. Bridge-unavailable errors use a stable error id, state the required component, and do not prevent non-bridge command import/execution. Unknown operation ids are rejected.
- Audit and observability: No new external telemetry. Request correlation and sanitized operation/error identifiers may be logged through existing diagnostic infrastructure without secrets or unredacted sensitive paths.

### Operational capability contract amendment

The operational families previously grouped in S05 are delivered as three independently accepted command families. Existing exported cmdlet names remain the public compatibility surface. Their internal WorkspaceBridge operation identifiers are versioned and capability-specific; the Bridge accepts legacy unversioned identifiers only as temporary private aliases during migration and the module itself invokes only the versioned identifier. A legacy alias has the same typed payload, result, consent, and error behavior as its versioned counterpart and is removed only after all module callers and tests use the versioned route.

Each route accepts one typed JSON payload and returns a typed JSON result. Unknown fields, unsupported operation identifiers, missing preview/grant fields, unsafe paths, and stale fingerprints are rejected before Core execution. Stable sanitized error codes identify validation, preview, grant, and Bridge-unavailable failures without exposing raw host output or sensitive paths. Desktop migration remains a separate consumer slice: no S05 command implementation gives WPF a generic route, direct Core reference, or new host-I/O authority.

### Platform-integrated capability contract amendment

The current capability audit confirms that the public module already owns fixed read and preview/execute contracts for container runtime inventory and Podman user-unit/connection operations, but `IntegrationsTabViewModel` still directly invokes `IContainerRuntimeService` and `IPlatformCapabilityService`. That is a prohibited second product path under FR-001, FR-004, and FR-005. Slice S21 therefore closes this one coherent, already-specified capability family before the broader remaining S06 work.

| Requirement | Current evidence | S21 contract and ownership | Verification |
| --- | --- | --- | --- |
| FR-001, FR-005 | `IntegrationsTabViewModel` injects Core container and platform services; `Get-DistroNexusContainerRuntimeStatus` already calls the fixed `containerRuntimeStatus` route and `Get-DistroNexusCapability -Name <name> -InstanceOnly` already returns the fixed instance-capability route. | Add only typed `IPowerShellModuleClient` methods for container snapshot, instance capability snapshot, Podman unit preview/execute, and Podman connection preview/execute. The module client invokes the exported cmdlets only; the view model receives no Core container/platform service. | Client command-shape tests and view-model tests reject direct service use while preserving the `InstanceSystemd` gate. |
| FR-003, FR-007 | Existing Podman public commands expose Core-issued, single-use previews and use `ShouldProcess`; Core owns endpoint validation, fingerprints, expiry, and replay checks. The current typed module-client invocation seam serializes only scalar parameters. | Preserve pipeline `-Preview` compatibility and add strict scalar execute parameter sets: unit execution requires `PreviewToken`, `InstanceName`, `Unit`, and `Action`; connection execution requires `PreviewToken`, `InstanceName`, `ConnectionName`, and `Endpoint`. The client may pass only these explicit returned preview fields; it may not construct a token, submit arbitrary command text, or weaken Core endpoint validation. | Pester `WhatIf`/invalid-input/replay/scalar-parameter coverage and xUnit client command-shape tests. |
| FR-004, FR-006 | `containerRuntimeStatus`, `podmanUserUnit*`, and `podmanConnection*` are fixed Bridge routes. | No new generic route, script runner, container/image CRUD, installation, or Docker settings mutation is introduced. Core remains the internal implementation selected by the module. | Bridge unknown-operation and command allow-list tests; structural review of complete slice diff. |

The S21 public result models are the existing sanitized Core runtime, instance-capability, and Podman result records. `Get-DistroNexusContainerRuntimeStatus -Name` is the sole inventory entry point; `Get-DistroNexusCapability -Name <name> -InstanceOnly` is the sole source of the existing `InstanceSystemd` gate. The four existing Podman preview/execute cmdlets remain the sole mutation entry points and retain their current `ShouldProcess`, single-use preview, TTL, fingerprint, and safe-endpoint semantics. Execute cmdlets retain `-Preview` for existing pipeline callers, but expose only the explicit scalar parameter sets above for the typed desktop client; both parameter sets call the same fixed Bridge operation and Core-issued token validation. This avoids a generic object/script serializer in `PowerShellService`. WPF confirmation text is presentation only; it must call the matching typed module-client execute method after the module consent boundary, never call Core execute directly.

The following remaining platform families are intentionally not combined with S21 because their contracts are materially incomplete: WSLg pin/reveal needs an opaque discovery/revision contract; Docker integration needs a Core-issued preview token and atomic settings model; USB mutation needs an authenticated PowerShell-to-elevated-helper grant boundary; monitoring needs bounded session ownership/cancellation semantics; terminal/explorer and application update need allow-listed external-launch contracts. They remain S06 follow-up design work, not implied by S21 completion.

### WSLg discovery-grant contract amendment

`WslgApplication` is an internal authority-bearing model: it contains the distribution, executable, arguments, desktop-entry path, and icon path. The current unversioned `wslgDiscover`/`wslgLaunch` flow returns and accepts that model, while `ApplicationsViewModel` calls `IWslgApplicationService` directly for status, discovery, launch, pin, and reveal. Although Core rebinds a desktop entry before launch or reveal, the public object shape and second Desktop execution path violate FR-001, FR-004, FR-005, and FR-007. Slice S22 replaces only the WSLg presentation path with an opaque discovery-grant protocol.

| Requirement | Current evidence | S22 contract and ownership | Verification |
| --- | --- | --- | --- |
| FR-001, FR-005 | `ApplicationsViewModel` injects `IWslgApplicationService`; the existing module start cmdlet accepts a caller-supplied application object. | The view model receives only typed `IPowerShellModuleClient` WSLg methods. It retains visual selection/filter state and a private discovery token, but has no Core WSLg service. `CopyCommand` is removed because a public projection must not restore executable or argument disclosure merely for presentation. | Structural view-model test, fixed-cmdlet client tests, and behavior tests for refresh, launch, pin, reveal, unavailable state, and stale-token clearing. |
| FR-003, FR-007 | Each module-client command invocation starts a fresh PowerShell/Bridge process, so an in-memory discovery token would be lost between discovery and action. Existing Core re-reads and validates entries before `wsl.exe --exec`. | `wslg.discover.v1` issues a cryptographically random, opaque, 2-minute discovery token stored in a per-user protected, integrity-checked, hash-addressed Core grant record. The record binds distribution, discovered descriptors, expiry, and schema version; it is bounded, reusable until expiry, and deleted best-effort. Action routes accept only token, application id, and pin state where applicable; Core resolves the grant and re-reads/re-parses the entry before launch or reveal. | Expired, forged, foreign, altered-entry, and unknown-application tests prove that no `wsl.exe` action occurs. Tests also prove the public projection omits executable, arguments, and filesystem paths. |
| FR-003, FR-004, FR-006 | Public WSLg commands currently use unversioned Bridge operations, and no pin/reveal public command exists. | New fixed routes are `wslg.status.v1`, `wslg.discover.v1`, `wslg.launch.v1`, `wslg.reveal.v1`, and `wslg.pin.v1`. Exact payloads reject unknown fields. `Get-DistroNexusWslgStatus`, `Get-DistroNexusWslgApplication`, `Start-DistroNexusWslgApplication`, `Show-DistroNexusWslgApplicationEntry`, and `Set-DistroNexusWslgApplicationPin` are the sole public family; all actions use `ShouldProcess`. | Bridge protocol tests reject legacy/unknown/malformed shapes; Pester verifies validation and `WhatIf` prevents action routes. |

`Get-DistroNexusWslgApplication -Name` returns `WslgDiscoveryResult`: the availability status, opaque token and expiry when available, and `WslgApplicationProjection` rows containing only application id, display name, categories, pin state, and bounded icon bytes. The distribution is supplied by the caller and therefore not repeated in each row. The result contains no executable, arguments, desktop-entry path, or icon path. The former authority-bearing `Start-DistroNexusWslgApplication -Application` parameter set is removed rather than silently accepting a tamperable legacy input.

The protected grant store is WSLg-specific, lives beneath the existing per-user application data root, never stores the raw token in its file name, and enforces expiry on every load. It uses create-new/replace-safe file behavior plus an interprocess lock appropriate to the local user; a process-local `VersionedJsonStore` lock is insufficient. The token is a bearer capability scoped only to the current user and the short-lived, read-only discovery snapshot. It may be retried during its lifetime so pin/reveal/launch failures remain recoverable; action revalidation remains the final authority. Bridge errors use stable redacted codes (`Wslg.DiscoveryGrantInvalid`, `Wslg.DiscoveryGrantExpired`, `Wslg.ApplicationNotFound`, and `Wslg.EntryChanged`) and never echo a token, host path, executable, or raw process error.

### Docker Desktop integration contract amendment

The current Docker integration is a prohibited dual execution path: `IntegrationsTabViewModel`, `MainViewModel`, and an instance command resolve `IDockerIntegrationService` directly, while the existing `Get-`, `Enable-`, and `Disable-DistroNexusDockerIntegration` module commands independently inspect and write Docker Desktop settings. Both paths expose or derive host paths and mutation currently lacks a Core-issued preview, content fingerprint, atomic replacement, or cross-process-safe state transition. Slice S23 makes the Core service the only Docker settings authority, reached solely through fixed PowerShell commands and typed module-client methods.

| Requirement | Current evidence | S23 contract and ownership | Verification |
| --- | --- | --- | --- |
| FR-001, FR-005 | WPF directly queries and mutates `IDockerIntegrationService`; existing module scripts separately manipulate settings JSON. | `IPowerShellModuleClient` exposes only typed Docker snapshot, preview, and execute methods. Every Docker status consumer and toggle path uses it; WPF renders results, requests confirmation, and never receives a settings path or raw document. | Structural checks reject `IDockerIntegrationService` from migrated view models; module-client command-shape and view-model preview/decline/execute tests. |
| FR-003, FR-004, FR-006 | No Docker Bridge route or preview/execute protocol exists. | Fixed routes are `docker.integration.get.v1`, `docker.integration.preview-set.v1`, and `docker.integration.set.v1`. Public `Get-DistroNexusDockerIntegration`, `Get-DistroNexusDockerIntegrationPreview`, and `Set-DistroNexusDockerIntegration` are the primary commands. Legacy `Enable-` and `Disable-` remain thin compatibility facades only: they obtain a preview then call the same `ShouldProcess`-protected set contract; they never parse or write settings. | Exact-payload Bridge tests, public-command validation/WhatIf tests, and fixed-cmdlet allow-list tests. |
| FR-003, FR-007 | Current Core writer creates missing files, fails open when the instance cannot be determined, and directly overwrites settings. | Preview requires Docker Desktop, a known WSL2 non-reserved instance, an existing parseable selected settings file, and captures file identity plus content fingerprint. Execution consumes a single-use short-TTL protected grant bound to name, desired state, selected identity, and fingerprint; it rechecks all fields then atomically replaces only `integratedWslDistros`, preserving unrelated JSON. It rejects missing, malformed, duplicate/non-string array content, file switching, and state drift. | Invalid/WhatIf/expired/reused/mismatched/stale-token tests prove no write; atomic writer and preservation/deterministic-deduplication tests cover the successful path. |

`DockerIntegrationSnapshot` contains only availability, eligibility/reason, status, sanitized version, and restart guidance. `DockerIntegrationPreview` contains a Core-issued opaque token, bound state, expiry, effects, and redacted warnings; it contains no settings path, file identity, raw JSON, registry value, or executable path. `DockerIntegrationResult` contains success, stable outcome code, restart-required status, and guidance. The grant is durable across independent PowerShell/Bridge processes, protected and integrity-checked for the same user, hash-addressed without the raw token, short-lived, bounded, and atomically consumed. Stable errors distinguish invalid, expired, replayed, and stale previews without revealing a path or document content.

The dedicated Docker settings writer uses a bounded DistroNexus cross-process lock, verifies the selected file identity and fingerprint at execution, writes a flushed temporary sibling, and performs one atomic replace with a backup. It never creates a settings file, accepts an environment/path override, restarts Docker Desktop, alters Docker contexts/machines/storage, or retries a conflict blindly. Every detected identity/fingerprint/sharing conflict fails closed and preserves a readable original or backup. A third-party Docker Desktop writer does not participate in DistroNexus locking and Windows has no portable compare-and-swap primitive spanning arbitrary writers and `File.Replace`; therefore repository tests can prove DistroNexus-vs-DistroNexus serialization and fail-closed detected conflicts, but cannot prove absence of every external write race. External Docker Desktop concurrent-write behavior is a named UAT closure gate and must not be claimed as repository-proven. Compatibility facades retain their existing names but cannot bypass `ShouldProcess`, Core validation, the grant, or the atomic writer.

### Monitoring pull and process-action contract amendment

`MonitorTabViewModel` currently owns a live `IMonitoringSession`, subscribes to Core events, polls Core directly, and sends process signals through Core previews. The public module exposes only an unversioned one-shot snapshot. A remote durable monitoring session is not suitable because every module-client call starts a fresh PowerShell/Bridge process; it would introduce daemon ownership, leak, and cancellation risks. Slice S24 replaces the WPF/Core path with bounded stateless pull requests and durable, Core-owned action grants.

| Requirement | Current evidence | S24 contract and ownership | Verification |
| --- | --- | --- | --- |
| FR-001, FR-005 | The monitoring tab receives `IMonitoringService`, owns a session/event stream, thresholds, and process actions. | The view model receives only `IPowerShellModuleClient`; it owns a Dispatcher timer, cancellation, and a bounded local display history. Every sample/action is a fixed module call; it has no Core session/service or process authority. | Lifecycle/cancellation tests prove no polling while hidden, no late updates, and no direct monitoring service dependency. |
| FR-003, FR-004, FR-006 | The current module only maps unversioned `monitorSnapshot`; in-memory session previews and KILL eligibility cannot cross module processes. | Fixed routes are `monitoring.snapshot.v1`, `monitoring.process.preview.v1`, and `monitoring.process.execute.v1`. Snapshot returns a sanitized public sample plus a short-lived snapshot grant. Preview accepts only snapshot token, PID, and allow-listed action; execute accepts only a Core preview token and uses `ShouldProcess`. | Exact payload, unknown-field, cmdlet allow-list, WhatIf/decline, forged/expired/reused token, and no-signal tests. |
| FR-003, FR-007 | Existing Core uses fixed probes, PID/start-time revalidation, TERM-to-KILL sequencing, bounded samples, and no automatic escalation. | Every request creates/starts/stops/disposes one bounded Core session in `finally`, never starts a distribution, and returns at most 20 sanitized processes/128 ports. Durable grants bind distribution, PID/start ticks, action, expiry, and snapshot identity. KILL requires durable TERM eligibility plus a fresh preview; execution rechecks running state and PID identity immediately before signal. | Stopped instance/cancellation/disposal, process identity drift, TERM/KILL/replay, and public-redaction tests. |

`Get-DistroNexusMonitoringSnapshot -Name -IntervalSeconds` calls `monitoring.snapshot.v1` with only the fixed interval set 1/2/5/10; the Bridge applies a bounded deadline and always disposes. Its public result excludes `CounterState`, raw stderr, paths, and unbounded process arguments; command text is sanitized/truncated. `Get-DistroNexusMonitoringProcessActionPreview -SnapshotToken -ProcessId -Action` issues a durable preview. `Invoke-DistroNexusMonitoringProcessAction -PreviewToken` is the sole signal execution command and has `ShouldProcess`; neither command accepts a process object, raw signal, shell script, command arguments, or nice value. Snapshot/action/TERM-eligibility records are same-user protected, integrity-checked, hash-addressed opaque grants with mandatory expiry; action previews are atomically single-use.

The monitoring UI runs only while visible. It permits one outstanding pull, ignores a result after cancellation/deactivation/instance change, and caps its own display history at 300. It does not own a background Core session. No persistent bridge daemon, automatic KILL, WSL start/restart, telemetry upload, arbitrary sampling script, or system-wide process control is introduced.

### USB action-grant and trusted-elevation-broker contract amendment

`UsbDevicesViewModel` currently calls `IUsbDeviceService` directly for discovery and all four actions. The exported USB cmdlets independently invoke `usbipd` and do not cover Bind/Unbind. That creates two incompatible product paths and cannot safely reuse the in-memory Core preview map across the one-process-per-module-call boundary. More importantly, the existing elevated helper correctly accepts a pipe server only when it is the signed Desktop executable; allowing generic `powershell.exe` or `dotnet.exe` would weaken the privileged boundary. Slice S25 replaces both paths with fixed module contracts and a narrowly trusted product-owned broker.

| Requirement | Current evidence | S25 contract and ownership | Verification |
| --- | --- | --- | --- |
| FR-001, FR-005 | `UsbDevicesViewModel` injects `IUsbDeviceService`; public Connect/Disconnect scripts duplicate direct native preflight and execution. | The view model uses only typed USB methods on `IPowerShellModuleClient`. Module commands are the sole public discovery/preview/execute path; compatibility Connect/Disconnect commands become facades. | Structural view-model/client tests and Pester tests prove no WPF/direct-native bypass. |
| FR-003, FR-006 | Core validates `UsbBusId`, hardware identity, state transitions and version profiles, but previews are in memory. | Fixed routes are `usb.status.v1`, `usb.list.v1`, `usb.action.preview.v1`, and `usb.action.execute.v1`. Preview accepts exactly action, BusId and optional DistributionName; execute accepts only an opaque token. Unknown fields and unsuitable action/distribution combinations are rejected before adapter invocation. | Exact-payload, `WhatIf`, legacy-facade, malformed/unknown-field and no-tool-on-rejection tests. |
| FR-003, FR-007 | Bind/Unbind use the signed helper, which validates pipe SID/PID/nonces and trusted `usbipd`, but presently trusts only Desktop. | Core issues a same-user protected, hash-addressed, short-lived action grant bound to action, BusId, HardwareId, distribution and current-state fingerprint. A new signed `DistroNexus.UsbElevationBroker` is the sole additional helper-approved pipe server. It consumes the grant and preserves the existing helper proof protocol; the helper trusts exactly signed Desktop or signed broker product identity, never PowerShell, dotnet, caller paths, admin membership, or a filename. | Forged/expired/replayed/wrong-user grants, UAC decline, BusId reuse/state drift, malformed pipe proof and untrusted caller tests prove no privileged tool action. |

`Get-DistroNexusUsbIpdStatus` and `Get-DistroNexusUsbDevice` expose only sanitized status/device projections. `Get-DistroNexusUsbDeviceActionPreview -Action -BusId [-DistributionName]` emits an opaque Core-issued preview token, safe display/effects/warnings, elevation requirement and expiry; it never emits HardwareId, executable arguments, paths, serials or raw tool output. `Invoke-DistroNexusUsbDeviceAction -PreviewToken` is the sole action command and uses `ShouldProcess` with High impact. Connect/Disconnect remain thin deprecated facades that request a preview and then invoke this route; Bind/Unbind are available only through the same preview/execute contract.

Action grants use a 256-bit base64url token, CurrentUser-protected integrity-checked record, token-hash file name, schema/version, issuing SID, strict expiry of at most two minutes, bounded cleanup and an interprocess lock. Execution atomically reserves the grant before any UAC request and permanently retires it on decline/cancellation or completion. Core repeats current usbipd/profile/device/HardwareId/legal-transition validation immediately before Attach/Detach. Bind/Unbind pass only the token to the trusted broker, which loads the protected grant and performs the existing SID-limited-pipe, nonce, PID and helper-proof flow; the existing elevated helper remains the final `usbipd.exe` signature, JSON and state authority immediately before mutation.

Discovery may report parseable unavailable state, but Preview/Execute fail closed when usbipd is missing, stopped or unsupported. No route accepts native arguments, device paths, service control, Windows-feature mutation, install/driver setup, a raw USB/IP command, or a persistent watch. Attach preserves the existing VM-wide/storage warning and advisory `lsusb` guidance without starting a distribution. WMI change watching is presentation-only and may only trigger a typed refresh; it has no operation authority. Real signing, UAC, helper/broker packaging and physical-device execution are explicit external UAT gates.

### Path-bearing lifecycle, secret, and compaction contract amendment

S36 establishes the shared safety contract before any remaining lifecycle implementation. User-selected lifecycle paths are local fixed-volume Windows paths only: PowerShell performs grammar checks (nonempty, bounded, rooted, no control/NUL characters); Core canonicalizes with `Path.GetFullPath`, rejects UNC, device, root/system directories and every reparse-point traversal, and permits only an explicitly user-approved local root. It builds the final install target as `<approved-root>/<validated-instance-name>`, rejects aliases, collisions and nonempty targets, and reserves/revalidates immediately before creation or import. Paths never appear in execute requests or public results; results contain only a sanitized outcome and an optional display-safe target label. Core owns application cache and staging roots.

Every path-bearing mutation is fixed preview/execute: `instance.remove.preview.v1 { Name, KeepFiles }`, `instance.move.preview.v1 { Name, Destination }`, `instance.rename.preview.v1 { Name, NewName }`, `instance.export.preview.v1 { Name, Destination, StopRunning }`, `instance.import.preview.v1 { Name, Source, InstallPath }`, and their corresponding `.execute.v1 { PreviewToken }`. Previews issue same-user protected, hash-addressed, short-lived, atomically single-use grants bound to canonical request, registered identity, state/fingerprint and operation. Execute revalidates state/path/reservation and accepts no replacement field. Remove is irreversible and claims no rollback. Move/rename stage only in Core-owned temporary storage, verify export before unregister, verify resulting registration, and report a stable recovery action if their rollback cannot restore the prior registered identity. No Core implementation may fall back to a raw WSL script or an alternate command after a module/Bridge contract failure.

Package acquisition and install are separate consent boundaries. A read-only resolve command describes catalog/cache provenance without exposing a host path. `Save-DistroNexusPackage` is the sole acquisition mutation and returns an immutable verified package reference. The install preview accepts only that reference, an instance name, allowed local-root choice and non-secret modeled options; it rejects missing/unverified artifacts and never downloads. Its execute token runs only controlled Core staging/import, cleans up only the distribution it created after identity verification, and reports separate acquisition/install cancellation or rollback outcomes. Initial-user configuration and credential change use a dedicated secret-bearing invocation path: secret values are bound directly to the module/runspace and are neither formatted into script text nor stored in `InstallOptions`, wizard state, command dictionaries, logs, errors or result records. The module passes secrets to the fixed Linux credential operation through a non-command-line channel and clears it in `finally`.

Compaction uses `instance.compact.preview.v1 { Name }` and `instance.compact.execute.v1 { PreviewToken }`. Preview is read-only and returns exact current size, `EstimateKind` (`Unknown`, `UpperBound`, or `Measured`), prerequisites and warnings; it never labels current size as a reclaim estimate, stops WSL, runs `fstrim`, or creates a grant when `WhatIf`/consent declines. Execute consumes the token once, rechecks registered identity/state/VHDX identity, uses only its fixed compaction methods, preserves prior running state, and returns sanitized before/after/saved/method/restart outcomes. All lifecycle/compaction public mutations use `SupportsShouldProcess`; `-Force` never bypasses `WhatIf`.

Path fields have fixed semantics. `move.preview.Destination` and `import.preview.InstallPath` are an approved local destination root, not an arbitrary final directory; Core derives the final target as `<root>/<validated Name>`. `export.preview.Destination` is an exact local archive filename beneath an approved local root, must end in `.tar`, must not already exist, and cannot be a directory or overwrite request. `import.preview.Source` is an existing regular local `.tar` file beneath an approved local root; it is never an application cache reference. Remove and rename accept no path. An approved root is represented only by its bounded preview input path; the resulting grant records a Core-generated path identity and canonical target, neither of which is exposed on execute or in public results. UNC, device, removable and reparse-derived roots are rejected in this release.

Package resolution and acquisition use fixed records. `install.source.resolve.v1 { PackageId }` is read-only and returns `{ PackageId, CacheState, DownloadAvailable, ExpectedSha256, ExpectedSizeBytes, SourceProvenance }`, with no local path. `package.acquire.preview.v1 { PackageId }` returns a reviewed acquisition preview; `package.acquire.execute.v1 { PreviewToken }` performs the single download/cache mutation and returns `{ PackageReference, PackageId, Sha256, SizeBytes, ExpiresAt, OutcomeCode }`. `PackageReference` is a Core-issued, same-user protected, hash-addressed opaque record bound to package id, canonical cache identity, SHA-256, size, provenance, issuance and expiry. It is invalidated if the cache file is deleted, replaced, mismatches hash/size, expires, or is from another SID. It is not a path and cannot be supplied by a caller.

Install routes are `instance.install.preview.v1 { PackageReference, Name, InstallRoot, Username, Shell, Locale, SetAsDefault, SecretEnvelope? }` and `instance.install.execute.v1 { PreviewToken }`. `InstallRoot` has the fixed root meaning above; `Username`, `Shell`, `Locale` and `SetAsDefault` are the complete allow-listed non-secret option set. Interactive mode, auto-download, open-terminal, raw init commands, package paths, distribution command lines and all unknown fields are rejected. `SecretEnvelope`, when present, is a bounded CurrentUser-DPAPI envelope created by direct secure parameter binding in the module; it is never emitted, logged, or stored in Desktop/Core option models. Core persists it only inside the protected preview grant, bound to the SID, instance identity, username and expiry, and decrypts it only immediately before the fixed Linux user-configuration call. `ShouldProcess` is evaluated before preview/grant creation; a declined operation produces no envelope/grant or acquisition/install mutation.

Credential change follows the same no-script-text rule. `instance.credential.preview.v1 { Name, Username, SecretEnvelope }` accepts the module-created secure envelope only after the public `Set-DistroNexusCredential -Password SecureString` binding; it returns a reviewed non-secret preview. `instance.credential.execute.v1 { PreviewToken }` is the only mutation route and atomically consumes a same-user, short-lived token bound to instance identity, normalized username, secret-envelope identity and state fingerprint. The module client invokes the cmdlet with a directly bound secure parameter, not a generated command dictionary or string. The public success record is exactly `{ Succeeded, InstanceName, OutcomeCode }`; public errors use stable `Lifecycle.CredentialInvalid`, `Lifecycle.CredentialGrantInvalid`, `Lifecycle.CredentialGrantExpired`, `Lifecycle.CredentialStateChanged`, or `Lifecycle.CredentialFailed` codes and never include secret text or command text. The secret envelope and its protected grant are deleted in `finally` on success, decline, cancellation, failure or expiry. Replay, SID mismatch, secret/envelope mismatch and cancellation before fixed execution fail closed.

Every path-bearing operation records a durable Core recovery record before its irreversible commit point. Export's commit point is successful atomic final archive placement; cancellation before it deletes only a Core-owned temporary archive, while cancellation after it reports `Lifecycle.ExportCompletedAfterCancellation` without deleting the caller destination. Import's commit point is successful registration of the new identity; cancellation before it removes only the reserved empty target, while cancellation after it reports `Lifecycle.ImportRecoveryRequired` and retains the registered identity for explicit follow-up. Install uses the same import checkpoint and may unregister only the identity created by its own grant. Move/rename commit on verified destination registration and then remove their staging archive; a failed restore reports `Lifecycle.RollbackFailed` with a durable recovery id. Every result has only `{ Succeeded, Operation, InstanceName, OutcomeCode, RecoveryAction?, RecoveryId? }`; `RecoveryAction` is one of `None`, `RetryRecovery`, or `ManualRecoveryRequired`, and no result includes a path or archive name.

S37 implements the shared grants/path resolver/outcome models and fixed path-bearing lifecycle routes. S38 implements verified acquisition/install and safe secret transport, including both wizard paths. S39 implements compaction and disk presentation migration. Each has explicit negative/path/token/rollback/redaction tests. Production UAT must cover local-root denial/reparse/UNC rejection, corrupt/missing packages, password metacharacters, user cancellation at acquisition and install, WSL move/rename recovery, Optimize-VHD/diskpart privilege outcomes, and confirmation that logs/diagnostics do not expose secrets or sensitive paths.

## Data and Execution Semantics

- Data ownership and retention: Core owns settings, cache, catalog, backup, recovery, templates, and configuration persistence. Desktop never writes those stores. Existing retention and cleanup policies remain unchanged.
- State, transactions, idempotency, concurrency: Keep existing atomic replacement, journal/recovery, preview token, fingerprint, and grant semantics. Commands that start monitoring or streams define disposal and cancellation; no background state is owned by the WPF view model.
- Failure, retry, cancellation, recovery: Every bridge request receives cancellation. The module translates a typed bridge failure to a non-secret PowerShell error. No automatic retry is added for destructive commands. Partial-operation recovery remains in Core and is surfaced through command results/errors.

## Security and Operations

- Threat/secret controls: Desktop cannot tunnel arbitrary scripts. The module cannot expose arbitrary bridge operations. Preserve path containment, archive validation, signature/trust checks, elevation grants, secure string handling, and error redaction.
- Runtime/deployment constraints: Bridge resolution is lazy and deterministic. The packaged bridge remains an explicit dependency only for command families that use it; module-only commands continue to import when it is absent. A bridge-backed invocation without the runtime fails with the stable `DistroNexus.WorkspaceBridgeUnavailable` error id. Development resolution must not be silently preferred over the packaged runtime when both exist.
- External acceptance: Real WSL lifecycle, Windows feature repair, elevated USB attach/detach, systemd/network mutation, and GUI application launch require a disposable Windows/WSL UAT host. Those results are release evidence, not repository-test substitutes.
