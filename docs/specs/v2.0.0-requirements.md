# DistroNexus 2.0.0 Requirements Specification

## 1. Overview
The current version (v1.x) is a WSL management tool built with a hybrid architecture using Golang (Fyne GUI) and PowerShell scripts.

As the project evolves, to better leverage Windows platform native capabilities, improve UI modernization (such as better high-DPI support and more native Windows controls), and unify the technology stack to reduce maintenance costs, a comprehensive technical refactoring is planned for version 2.0.0.

**Core Objective:**
Migrate the client completely to the .NET technology stack and refactor the underlying PowerShell scripts into a formal PowerShell module.

## 2. Technology Stack Analysis

### 2.1 Client Technology Comparison
| Feature | Option A: WPF (.NET 10) | Option B: Blazor Hybrid (WPF/WinForms Host) |
| :--- | :--- | :--- |
| **Advantages** | - Mature and stable, de facto standard for Windows desktop development<br>- Extremely powerful UI customization capabilities (XAML)<br>- Perfect MVVM pattern support<br>- Excellent performance with native controls<br>- Rich third-party control libraries (HandyControl, MahApps, DevExpress, etc.) | - Ability to reuse web frontend technologies (HTML/CSS)<br>- Modern UI development experience<br>- Cross-platform potential (easier future migration to MAUI) |
| **Disadvantages** | - Steeper learning curve (XAML)<br>- Windows-only platform (though current requirement is Windows-only) | - Potentially heavier than pure native apps when running on desktop<br>- Web rendering layer may be unnecessary for pure system utility applications |
| **Recommendation** | **Strongly Recommended (Option A - WPF)** | Alternative |

**Recommendation Rationale:**
DistroNexus is a tool that deeply depends on Windows system APIs and WSL command-line interactions. WPF provides the most native Windows desktop experience. For this type of system utility, users typically expect fast startup, reasonable resource usage, and UI that harmonizes with the operating system. WPF combined with modern UI libraries (such as WPF UI or HandyControl) can easily create Windows 11-style interfaces and handle complex system interaction logic more effectively.

### 2.2 Script Layer Refactoring
- **Current State**: Scattered individual `.ps1` scripts in the `scripts/` directory with dispersed invocations, difficult maintenance, and duplicated code for state management (logging, configuration loading).
- **Target**: Refactor into a single **PowerShell Module (`DistroNexus.psm1`)**.
  - Encapsulate as Cmdlet format (e.g., `Install-WslDistro`, `Get-WslInstance`).
  - Unified error handling and logging mechanism.
  - Easier to invoke from C# layer (via System.Management.Automation or direct Process calls).

## 3. Feature Migration Requirements

### 3.1 Core Features (Complete Preservation)
1.  **Dashboard (Home)**: Display installed instance list.
    *   Status display (Running/Stopped).
    *   Quick actions: Start, Stop, Open Terminal.
2.  **Installation Wizard**:
    *   Support online download from official sources.
    *   Support custom installation paths (non-C drive).
    *   Support custom username/password configuration.
3.  **Advanced Instance Management**:
    *   **Move**: Migrate VHDX file location.
    *   **Rename**: Modify registration name.
    *   **Credential Management**: Reset password/user.
4.  **Package Management**:
    *   Local cache management.
    *   Offline installation support.
5.  **Global Settings**:
    *   Default path configuration.
    *   Network source configuration.

### 3.2 Improvements
- **Performance**: Direct C# invocation of PowerShell API may be more efficient and controllable than Go launching `powershell.exe` subprocesses.
- **UI/UX**: Adopt Fluent Design System style with dark/light theme switching support.

## 4. Development Roadmap

### Phase 1: PowerShell Module Refactoring
1. Create `DistroNexus.Core` module.
2. Migrate existing script logic to module functions:
   - `install_wsl_custom.ps1` → `Install-DistroNexusInstance`
   - `scan_wsl_instances.ps1` → `Get-DistroNexusInstance`
   - etc.
3. Unit Testing: Write tests for core logic using Pester.

### Phase 2: .NET Client Development (WPF)
1. Initialize WPF project structure (MVVM Toolkit + Dependency Injection).
2. UI framework selection (recommend `WPF UI` or `MaterialDesignInXamlToolkit`).
3. Implement service layer:
   - `IPowerShellService`: Interface with underlying PS module.
   - `IDownloadService`: File downloads (using HttpClient with resume support).
   - `ISettingsService`: JSON configuration read/write.
4. Page migration development.

### Phase 3: Integration and Testing
1. Replace existing Golang build process.
2. Create new installer or portable version packaging process.
