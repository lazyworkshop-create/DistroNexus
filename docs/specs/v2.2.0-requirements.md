# DistroNexus v2.2.0 Requirements Specification

**Version**: 2.2.0
**Date**: 2026-03-01
**Status**: Draft
**Branch**: feat/v2.2.0

---

## 1. Release Goal

v2.2.0 focuses on **deep instance management enhancements**, elevating the existing basic lifecycle operations (start, stop, move, delete) into a full operational capability. The release is structured around two primary features — disk compaction and Docker Desktop integration — plus nine targeted enhancements spanning backup workflows, configuration visibility, network diagnostics, organisation tooling, and internal architecture. Together, these eleven items close the most impactful gaps identified through project analysis and WSL ecosystem research.

## 2. New Feature Requirements

### F-01 VHDX Disk Compaction

#### Background

Each WSL2 distribution stores its Linux filesystem in an `ext4.vhdx` file. When files are deleted inside Linux, the VHDX does not shrink automatically. Over time, the gap between the VHDX file size and actual disk usage can grow to tens of gigabytes.

#### Feature Description

Provide a one-click disk compaction capability for each instance. After execution, unused space inside the VHDX is reclaimed and the file size on Windows is reduced to close to actual usage.

#### Detailed Requirements

| ID | Requirement |
|----|-------------|
| F-01-1 | Automatically stop the target instance before compaction (if running); restore it to its previous state after compaction completes |
| F-01-2 | Run `fstrim -av` inside the instance before compaction to zero out deleted blocks, maximising the reclamation rate |
| F-01-3 | Prefer `Optimize-VHD` (Hyper-V module); automatically fall back to `diskpart compact vdisk` when Hyper-V is unavailable |
| F-01-4 | Show estimated reclaimable space (current VHDX size vs. actual usage) and require user confirmation before proceeding |
| F-01-5 | Display progress (percentage or phase text) during compaction; block all other operations on that instance while compaction is running |
| F-01-6 | Show the actual space saved (before/after comparison) when compaction completes |
| F-01-7 | On failure, surface a clear error message without corrupting the original VHDX |
| F-01-8 | Support bulk compaction (select multiple instances) |

#### PowerShell Cmdlet

```powershell
# New cmdlet
Compress-DistroNexusInstance [-Name] <string> [-WhatIf] [-Force]

# Parameters
-Name      # Target instance name
-WhatIf    # Estimate reclaimable space only; do not perform compaction
-Force     # Skip confirmation prompt
```

#### Implementation Notes

- Resolve VHDX path from registry: `HKCU:\Software\Microsoft\Windows\CurrentVersion\Lxss\{guid}\BasePath`
- Hyper-V module detection: `Get-Module -ListAvailable -Name Hyper-V`
- The `diskpart` path requires administrator privileges; check and prompt for elevation in advance
- Run `fstrim` via: `wsl -d <Name> -e fstrim -av`

#### UI Entry Points

- Instance detail panel → Disk section → **Compact Disk** button
- Instance list context menu → **Compact Disk**
- Bulk action toolbar (available when multiple instances are selected)

### F-02 Docker Desktop Integration Management

#### Background

Docker Desktop injects the Docker CLI into selected WSL distributions via its WSL Integration feature. Users currently have to navigate to Docker Desktop settings and toggle each distro individually, which breaks the management flow. DistroNexus can proxy this operation and provide a unified entry point.

#### Feature Description

Display the current Docker integration status for each instance in the instance detail panel, support one-click enable/disable, and detect whether Docker Desktop is installed.

#### Detailed Requirements

| ID | Requirement |
|----|-------------|
| F-02-1 | Detect whether Docker Desktop is installed (check executable path and version) |
| F-02-2 | Read Docker Desktop configuration and display the integration status per instance (Enabled / Disabled / Unavailable) |
| F-02-3 | Support enabling Docker integration for a specific instance (write the distro name to Docker Desktop config) |
| F-02-4 | Support disabling Docker integration for a specific instance |
| F-02-5 | When Docker Desktop is not installed, grey out the integration toggle and provide an install guidance link |
| F-02-6 | After a status change, prompt the user to restart Docker Desktop for the change to take effect |
| F-02-7 | Disable the Docker integration toggle when the instance is WSL v1 (Docker requires WSL v2) |
| F-02-8 | Exclude `docker-desktop` and `docker-desktop-data` internal distributions from this feature |

#### PowerShell Cmdlets

```powershell
# New cmdlets
Get-DistroNexusDockerIntegration [-Name] <string>
Enable-DistroNexusDockerIntegration [-Name] <string>
Disable-DistroNexusDockerIntegration [-Name] <string>
```

#### Implementation Notes

- Docker Desktop config file path: `%APPDATA%\Docker\settings-store.json` (4.30+) or `%APPDATA%\Docker\settings.json`
- Relevant config fields:
  ```json
  {
    "wslEngineEnabled": true,
    "enableIntegrationWithDefaultWslDistro": true,
    "integratedWslDistros": ["Ubuntu-22.04", "Debian"]
  }
  ```
- After writing the config, Docker Desktop must be restarted (via `docker-desktop` Windows service or `Docker Desktop.exe --quit` followed by relaunch)
- Handle write conflicts when Docker Desktop is running

#### UI Entry Points

- Instance detail panel → **Integrations** tab → Docker integration toggle
- Instance list: new Docker integration status icon column

## 3. Enhancement Requirements

### E-01 Instance Export and Import (UI Layer)

#### Background

`Move-DistroNexusInstance` already uses `wsl --export` / `wsl --import` internally to relocate instances, but the GUI exposes no standalone backup-export or restore-from-TAR operation. Users who want to archive an instance or restore from a previously saved TAR must fall back to the command line.

#### Feature Description

Add dedicated Export and Import actions to the GUI so users can create portable TAR archives of any instance and restore or clone instances from existing archives — without touching the terminal.

#### Detailed Requirements

| ID | Requirement |
|----|-------------|
| E-01-1 | Provide an **Export Instance** action that saves the selected instance to a user-chosen TAR file path via `wsl --export` |
| E-01-2 | Show a file-save dialog pre-populated with `<InstanceName>-<YYYYMMDD>.tar` as the default filename |
| E-01-3 | Display export progress (bytes written / elapsed time) while the export is running; disable all other actions on the instance during the operation |
| E-01-4 | Provide an **Import Instance** action that creates a new instance from a user-chosen TAR file via `wsl --import` |
| E-01-5 | The import dialog must collect: new instance name, install path (folder picker), and source TAR file |
| E-01-6 | Validate that the target instance name does not already exist before starting the import |
| E-01-7 | After a successful import, add the new instance to the list and select it automatically |
| E-01-8 | On export or import failure, display the error and leave the filesystem in its original state (no partial files) |
| E-01-9 | The **Export** action must be unavailable while the instance is running; prompt the user to stop it first or offer to stop it automatically |

#### PowerShell Cmdlets

```powershell
# New cmdlets
Export-DistroNexusInstance [-Name] <string> [-Destination] <string> [-Force]
Import-DistroNexusInstance [-Name] <string> [-Source] <string> [-InstallPath] <string>

# Parameters
-Name          # Instance name (Export: source; Import: name for the new instance)
-Destination   # Full path to the output TAR file
-Source        # Full path to the source TAR file
-InstallPath   # Directory where the new VHDX will be created
-Force         # Overwrite destination file if it exists (Export only)
```

#### Implementation Notes

- Export: `wsl --export <Name> "<DestinationPath>"`
- Import: `wsl --import <Name> "<InstallPath>" "<SourcePath>"`
- Wrap both in a progress-reporting shell that monitors output file growth (Export) or process output (Import)
- Validate free disk space on the destination drive before starting

#### UI Entry Points

- Instance detail panel → **Backup** section → **Export** and **Import** buttons
- Instance list context menu → **Export Instance**
- App toolbar → **Import Instance** (not tied to a specific instance row)

#### Acceptance Criteria

| # | Criterion |
|---|-----------|
| 1 | Exported TAR can be re-imported and produces a functional WSL instance |
| 2 | Progress indicator updates during long operations |
| 3 | Attempting to export a running instance shows a clear prompt |
| 4 | Import with a duplicate name is blocked with an explanatory message |

### E-02 .wslconfig Global Configuration Editor

#### Background

WSL global settings (`%USERPROFILE%\.wslconfig`) control memory limits, CPU count, swap size, and networking mode for all distributions. Currently there is no visual editor; users must locate and edit this INI file manually, which is error-prone and undiscoverable.

#### Feature Description

Add a dedicated `.wslconfig` editor section to the Settings page that reads and writes the file with validated form controls, eliminating the need to edit raw INI syntax.

#### Detailed Requirements

| ID | Requirement |
|----|-------------|
| E-02-1 | Read `%USERPROFILE%\.wslconfig` on Settings page load; create the file with safe defaults if it does not exist |
| E-02-2 | Expose the following `[wsl2]` parameters as labelled form controls: `memory` (text + unit selector MB/GB), `processors` (integer spinner), `swap` (text + unit selector, 0 = disabled), `localhostForwarding` (toggle), `networkingMode` (dropdown: NAT / mirrored / bridged / virtiofs) |
| E-02-3 | Validate each field before saving: `memory` and `swap` must be positive numbers; `processors` must be between 1 and the host logical CPU count |
| E-02-4 | Display the current host specs (total RAM, CPU count) as hints next to each field |
| E-02-5 | Show a **Restart WSL** button that runs `wsl --shutdown` after saving, since `.wslconfig` changes only take effect after a full WSL restart |
| E-02-6 | Provide an **Open Raw File** button that opens `.wslconfig` in the system default text editor |
| E-02-7 | Preserve any existing INI keys not exposed by the UI (do not discard unknown fields on save) |
| E-02-8 | Show a warning banner when the configured `memory` value exceeds 80 % of host RAM |

#### PowerShell Cmdlets

```powershell
# New cmdlets
Get-DistroNexusWslConfig
Set-DistroNexusWslConfig [-Memory <string>] [-Processors <int>] [-Swap <string>]
                         [-LocalhostForwarding <bool>] [-NetworkingMode <string>]

# Example
Set-DistroNexusWslConfig -Memory '4GB' -Processors 4 -Swap '2GB'
```

#### Implementation Notes

- File path: `[System.Environment]::GetFolderPath('UserProfile') + '\.wslconfig'`
- Parse as INI; use a lightweight INI read/write utility (no external dependency — custom `Get-IniContent` / `Set-IniContent` helpers already pattern in the PS layer)
- Preserve comments and unknown keys by reading the file as lines and replacing only matched key-value pairs

#### UI Entry Points

- Settings page → **WSL Global Configuration** section (new collapsible panel below existing settings)

#### Acceptance Criteria

| # | Criterion |
|---|-----------|
| 1 | Changes saved via the UI are correctly reflected in `.wslconfig` on disk |
| 2 | Unknown keys present before editing are not removed |
| 3 | Invalid input (e.g., `memory = abc`) is rejected with a field-level error message |
| 4 | After **Restart WSL**, `wsl -l -v` shows no running instances |

### E-03 Instance-Level Resource Configuration

#### Background

WSL 2.0+ supports per-instance sparse-mode via `wsl --manage <name> --set-sparse <true|false>`. Sparse mode allows the VHDX to automatically shrink as files are deleted, eliminating the need for manual compaction in most cases. This setting is currently invisible in the UI.

#### Feature Description

Surface per-instance WSL management properties — starting with sparse mode — in the instance detail panel, and allow users to toggle them without leaving the application.

#### Detailed Requirements

| ID | Requirement |
|----|-------------|
| E-03-1 | Display the current sparse mode status (`true` / `false`) for each WSL 2 instance in the instance detail panel |
| E-03-2 | Provide a toggle to enable or disable sparse mode per instance via `wsl --manage <Name> --set-sparse <true\|false>` |
| E-03-3 | Show a tooltip explaining that sparse mode enables automatic VHDX size reduction, and that enabling it on a large non-sparse VHDX does not immediately reclaim space |
| E-03-4 | Display the current global resource quotas (memory, CPU, swap) read from `.wslconfig` as read-only context, with a link to the `.wslconfig` editor (E-02) |
| E-03-5 | Disable all resource controls for WSL v1 instances (not applicable) |
| E-03-6 | If `wsl --manage` is unavailable (WSL < 2.0.0), hide the sparse mode control and show an upgrade prompt |

#### PowerShell Cmdlets

```powershell
# New cmdlets
Get-DistroNexusInstanceConfig [-Name] <string>
Set-DistroNexusInstanceSparseMode [-Name] <string> [-Enabled] <bool>

# Example output of Get-DistroNexusInstanceConfig
Name         : Ubuntu-22.04
SparseMode   : False
WslVersion   : 2
GlobalMemory : 8GB
GlobalCPUs   : 4
```

#### Implementation Notes

- Read sparse mode: `wsl --manage <Name> --set-sparse` has no get-only form; infer from VHDX file attributes or registry `SparseVhd` key under the distro's Lxss registry entry
- Write sparse mode: `wsl -d <Name> --manage --set-sparse true`
- Changing sparse mode does not require the instance to be stopped, but recommend a restart for immediate effect

#### UI Entry Points

- Instance detail panel → **Resources** tab (new tab, alongside existing Disk section)

#### Acceptance Criteria

| # | Criterion |
|---|-----------|
| 1 | Sparse mode status reads correctly for both sparse and non-sparse instances |
| 2 | Toggling sparse mode updates the value visible in `wsl --manage` output |
| 3 | Controls are hidden / disabled correctly for WSL v1 instances |

### E-04 Instance Backup Scheduling

#### Background

There is no automated backup mechanism. Users who want to protect instance data against accidental deletion or corruption must export manually and remember to do so regularly. A scheduled backup system backed by Windows Task Scheduler would provide reliable, hands-off protection.

#### Feature Description

Allow users to configure a per-instance backup schedule. The scheduler creates TAR archives on a recurring basis, manages retention, and integrates with Windows Task Scheduler so backups run even when the application is not open.

#### Detailed Requirements

| ID | Requirement |
|----|-------------|
| E-04-1 | Allow users to enable scheduled backups per instance with a configurable frequency: Daily, Weekly (day-of-week picker), or Monthly (day-of-month picker) |
| E-04-2 | Allow users to configure: backup destination folder, retention count (1–30), and the time of day for the backup job |
| E-04-3 | Create a Windows Task Scheduler task named `DistroNexus_Backup_<InstanceName>` that invokes `Invoke-DistroNexusBackup` at the configured schedule |
| E-04-4 | Enforce the retention policy after each backup: delete the oldest TAR files in the destination folder that exceed the configured count |
| E-04-5 | Provide an **Backup Now** button to trigger an immediate on-demand backup outside the schedule |
| E-04-6 | Show the backup history (timestamp, file size, status) for each instance — last 10 entries |
| E-04-7 | Stop the instance (if running), perform the export, then restart it if it was running — the same pre/post lifecycle as F-01 |
| E-04-8 | On backup failure, write the error to the application log and surface it as a notification in the UI on next launch |
| E-04-9 | Removing an instance should offer to delete its associated Task Scheduler task and backup files |

#### PowerShell Cmdlets

```powershell
# New cmdlets
New-DistroNexusBackupSchedule [-Name] <string> [-Destination] <string>
                               [-Frequency] <string> [-RetentionCount] <int>
                               [-Time] <TimeSpan>

Remove-DistroNexusBackupSchedule [-Name] <string>
Get-DistroNexusBackupSchedule [[-Name] <string>]

Invoke-DistroNexusBackup [-Name] <string> [-Destination] <string> [-RetentionCount] <int>

# Frequency values: Daily | Weekly:<DayOfWeek> | Monthly:<DayNumber>
```

#### Implementation Notes

- Task Scheduler integration: use `Register-ScheduledTask` / `Unregister-ScheduledTask` (built-in PowerShell cmdlets, no external dependency)
- Task action: `pwsh -NonInteractive -File "<ModulePath>\backup-runner.ps1" -InstanceName <Name>`
- Store schedule metadata in `%APPDATA%\DistroNexus\backup-schedules.json`
- Backup filename pattern: `<InstanceName>-backup-<yyyyMMdd-HHmmss>.tar`

#### UI Entry Points

- Instance detail panel → **Backup** tab → Schedule section and history table
- **Backup Now** button also lives in the **Backup** tab

#### Acceptance Criteria

| # | Criterion |
|---|-----------|
| 1 | A Task Scheduler task is created with the correct trigger after saving a schedule |
| 2 | Running the task produces a valid TAR archive that can be re-imported |
| 3 | Retention enforcement deletes the correct files when the count exceeds the limit |
| 4 | Removing the schedule deletes the Task Scheduler task |

### E-05 Port Forwarding Visualization

#### Background

Developers running servers inside WSL often lose track of which ports are active, which process owns them, and whether Windows-side port-proxy rules are in place. There is currently no way to inspect this from within DistroNexus.

#### Feature Description

Add a Network tab to the instance detail panel that lists all TCP/UDP ports being listened on inside the instance, together with any matching Windows `netsh interface portproxy` rules.

#### Detailed Requirements

| ID | Requirement |
|----|-------------|
| E-05-1 | List all listening TCP and UDP ports inside the instance by running `wsl -d <Name> -e ss -tlnp` and `wsl -d <Name> -e ss -ulnp` |
| E-05-2 | Display for each entry: protocol, local address, port, and process name / PID inside WSL |
| E-05-3 | Query Windows `netsh interface portproxy show all` and cross-reference results — highlight ports that have a matching Windows portproxy rule |
| E-05-4 | Provide a **Copy** button per row to copy the `host:port` string to the clipboard |
| E-05-5 | Provide a **Refresh** button to re-query the port list on demand |
| E-05-6 | Show a status indicator (Running / Stopped) — the port list is only available when the instance is running; show a placeholder message when it is stopped |
| E-05-7 | Display the instance's WSL IP address (from `wsl -d <Name> -e hostname -I`) at the top of the Network tab |

#### PowerShell Cmdlets

```powershell
# New cmdlet
Get-DistroNexusPortMapping [-Name] <string> [-Protocol <string>]

# Output fields: Protocol, LocalAddress, Port, ProcessName, Pid, HasWindowsProxy
```

#### Implementation Notes

- Parse `ss` output with a regex that captures `Local Address:Port` and `Process` columns
- Parse `netsh interface portproxy show all` as text table; match by `listenport`
- The WSL IP address changes on each WSL start; always fetch fresh — do not cache

#### UI Entry Points

- Instance detail panel → **Network** tab (new tab)

#### Acceptance Criteria

| # | Criterion |
|---|-----------|
| 1 | Ports shown match `ss -tlnp` output inside the WSL terminal |
| 2 | A port with a `netsh portproxy` rule is visually distinguished from one without |
| 3 | The Network tab shows a placeholder when the instance is stopped |
| 4 | The WSL IP address displayed matches `hostname -I` inside the instance |

### E-06 Instance Tagging and Grouping

#### Background

As the number of managed instances grows, a flat unfiltered list becomes hard to navigate. Users working across different contexts (personal dev, work, Docker-based projects) need a lightweight way to categorise and filter instances.

#### Feature Description

Allow users to attach one or more text tags to any instance. The instance list can then be filtered and grouped by tag. Tags are stored locally in `settings.json` and never affect the WSL instance itself.

#### Detailed Requirements

| ID | Requirement |
|----|-------------|

| E-06-2 | Display tags as chips / pills on the instance list row and in the instance detail header |
| E-06-3 | Provide a tag filter bar above the instance list; selecting one or more tags shows only instances that have all selected tags |
| E-06-4 | Support a **Group by tag** view that collapses the list into tag-labelled sections; instances with multiple tags appear in each relevant section |
| E-06-5 | Persist all tag data in `%APPDATA%\DistroNexus\settings.json` under an `instanceTags` map keyed by instance name |
| E-06-6 | When an instance is renamed, migrate its tags to the new name automatically |
| E-06-7 | When an instance is removed, delete its tag entries |
| E-06-8 | Provide a **Manage Tags** panel that lists all tags in use across all instances, with a rename-tag and delete-tag action (bulk operations) |

#### PowerShell Cmdlets

```powershell
# New cmdlets
Get-DistroNexusInstanceTag [[-Name] <string>]
Set-DistroNexusInstanceTag [-Name] <string> [-Tags] <string[]>
Add-DistroNexusInstanceTag [-Name] <string> [-Tag] <string>
Remove-DistroNexusInstanceTag [-Name] <string> [-Tag] <string>
```

#### UI Entry Points

- Instance list header → tag filter chips row
- Instance list row → tag chip display + inline **Add Tag** affordance
- Instance detail header → tag chips + **Edit Tags** button
- Settings page → **Manage Tags** section

#### Acceptance Criteria

| # | Criterion |
|---|-----------|

### E-07 Proactive Cache Invalidation

#### Background

The PowerShell instance cache (`Cache.ps1`) expires after a fixed 10-minute TTL. It has no awareness of actual WSL state changes. If a user starts or stops an instance outside the application (e.g., from a terminal), the UI shows stale data until the TTL expires or the user manually triggers a refresh.

#### Feature Description

Replace the passive TTL-only expiry strategy with an event-driven mechanism: monitor WSL process activity and invalidate the cache immediately when instance state changes are detected.

#### Detailed Requirements

| ID | Requirement |
|----|-------------|
| E-07-1 | Subscribe to Windows Management Instrumentation (WMI) process-creation and process-termination events for `wsl.exe` and `wslhost.exe` |
| E-07-2 | On detection of a relevant process event, mark the instance cache as stale and trigger a background refresh |
| E-07-3 | Throttle refresh triggers: if multiple events arrive within a 2-second window, coalesce them into a single refresh |
| E-07-4 | Keep the existing 10-minute TTL as a fallback for environments where WMI subscriptions are unavailable |
| E-07-5 | Show a subtle auto-refresh animation in the instance list header when a background refresh is in progress |
| E-07-6 | The proactive invalidation mechanism must not block the UI thread; all cache refresh work runs on a background thread / task |
| E-07-7 | Provide a `Get-DistroNexusCache` diagnostic cmdlet that shows the current cache age, entry count, and last-invalidated reason |

#### Implementation Notes

- C# side: use `System.Management.ManagementEventWatcher` with a WQL query:
  ```sql
  SELECT * FROM Win32_ProcessStartTrace WHERE ProcessName = 'wsl.exe'
  ```
  Repeat for `Win32_ProcessStopTrace`
- Invalidation signal: set a `CancellationTokenSource` that the cache-refresh loop monitors
- PowerShell side: extend `Cache.ps1` with an `Invalidate-InstanceCache` internal function callable from the C# host via `PowerShellService`

#### UI Entry Points

- No new UI surfaces; existing instance list auto-refreshes in response to events
- Subtle spinner in the list header during background refresh (non-blocking)

#### Acceptance Criteria

| # | Criterion |
|---|-----------|
| 1 | Starting an instance from the terminal causes the UI to show the updated state within 3 seconds |
| 2 | No UI freeze or jank during background cache refresh |
| 3 | With WMI disabled, the 10-minute TTL fallback still works correctly |

### E-08 Decouple PowerShell Service Layer

#### Background

`PowerShellService` in `DistroNexus.Core` spawns a new PowerShell process for every operation — instance listing, state queries, disk size calculation — and parses text output. This introduces latency (process spin-up overhead), creates fragility (output format changes break parsing), and makes unit testing difficult.

#### Feature Description

Progressively migrate core read-only operations from PowerShell process invocations to native C# implementations using direct `wsl.exe` CLI calls or registry reads. The public PowerShell module remains unchanged as a standalone user-facing tool; only the internal C# ↔ PS coupling is reduced.

#### Detailed Requirements

| ID | Requirement |
|----|-------------|
| E-08-1 | **Phase 1 — Instance listing**: replace the PS-based instance enumeration with direct parsing of `wsl --list --verbose --all` output in C# (`WslManagerService`) |
| E-08-2 | **Phase 1 — Disk size**: replace `Get-Item` invocation via PS with `FileInfo.Length` on the VHDX path resolved from the registry directly in C# |
| E-08-3 | **Phase 2 — Instance state polling**: replace state detection via PS with a direct `wsl --list --running` parse in C# |
| E-08-4 | **Phase 3 — Registry reads**: replace PS registry queries with `Microsoft.Win32.Registry` calls in C# (`RegistryKey.OpenBaseKey`) |
| E-08-5 | All migrated operations must have equivalent unit tests that mock `wsl.exe` output without spawning a real process |
| E-08-6 | `PowerShellService` is retained but its scope is reduced to operations that genuinely require PS (template execution, `fstrim`, credential setting) |
| E-08-7 | No change to the public PowerShell cmdlet API; the PS module continues to function independently |

#### Implementation Notes

- Parse `wsl --list --verbose` output format:
  ```
    NAME            STATE           VERSION
  * Ubuntu-22.04    Running         2
    Debian          Stopped         2
  ```
- Use `System.Diagnostics.Process` with redirected stdout; wrap in a `WslCliRunner` abstraction for testability
- Registry path for VHDX: `HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Lxss\{guid}\BasePath`

#### UI Entry Points

- No user-visible changes; this is a pure internal refactor
- Expected improvement: instance list load time reduced from ~800 ms to < 100 ms (eliminated PS process spin-up)

#### Acceptance Criteria

| # | Criterion |
|---|-----------|
| 1 | Instance list loads without spawning a PowerShell process (verify via Process Monitor) |
| 2 | All Phase 1 and Phase 2 paths have unit tests with mocked `wsl.exe` output |
| 3 | The public PS module cmdlets (`Get-DistroNexusInstance`, etc.) continue to pass all existing Pester tests |

### E-09 Unified Error Code System

#### Background

Error information in `DistroNexus.Core/Exceptions/` is communicated as free-form strings. Users and support workflows cannot reliably identify error categories, and tooling (logs, diagnostic scripts) cannot programmatically branch on error type. A structured error code system makes errors self-documenting and cross-referenceable.

#### Feature Description

Introduce a `DistroNexusErrorCode` enum and embed it in all exceptions, UI error messages, log entries, and PowerShell `ErrorRecord` objects. Pair codes with a reference table in the documentation.

#### Detailed Requirements

| ID | Requirement |
|----|-------------|
| E-09-1 | Define a `DistroNexusErrorCode` enum in `DistroNexus.Core` covering at minimum the categories: `InstanceNotFound`, `InstanceAlreadyRunning`, `InstanceAlreadyStopped`, `VhdxNotFound`, `VhdxAccessDenied`, `WslNotInstalled`, `WslVersionTooLow`, `DockerDesktopNotFound`, `DockerConfigWriteConflict`, `BackupDestinationFull`, `ExportFailed`, `ImportFailed`, `RegistryAccessDenied`, `UnknownError` |
| E-09-2 | Update `DistroNexusException` (and all subclasses) to carry a `DistroNexusErrorCode Code` property |
| E-09-3 | All `throw` sites in `DistroNexus.Core` must supply an appropriate error code |
| E-09-4 | UI error dialogs must display the error code alongside the human-readable message (e.g., `[DN-1001] Instance "Ubuntu-22.04" was not found`) |
| E-09-5 | Log entries written by `Logger.ps1` and NLog must include the error code as a structured field |
| E-09-6 | PowerShell cmdlets must populate `ErrorRecord.FullyQualifiedErrorId` with the error code string (e.g., `DistroNexus.InstanceNotFound`) |
| E-09-7 | Publish an `error-codes.md` reference document under `docs/development/` listing every code, its numeric value, description, and common causes |

#### Implementation Notes

- Assign stable numeric prefixes by category: `1xxx` = instance lifecycle, `2xxx` = disk/VHDX, `3xxx` = Docker integration, `4xxx` = backup/export, `5xxx` = configuration, `9xxx` = system/unknown
- Example mapping: `InstanceNotFound = 1001`, `VhdxNotFound = 2001`, `DockerDesktopNotFound = 3001`
- In PowerShell, surface via: `Write-Error -Message $msg -ErrorId "DistroNexus.$($code.ToString())" -Category $category`

#### UI Entry Points

- Error dialogs throughout the application gain a code prefix in the title bar and a **Copy Error Code** link

#### Acceptance Criteria

| # | Criterion |
|---|-----------|
| 1 | Every exception thrown by `DistroNexus.Core` carries a non-`UnknownError` code |
| 2 | UI error dialogs display the numeric code |
| 3 | Log files contain the error code as a structured field parseable by tooling |
| 4 | `error-codes.md` exists and covers all defined codes |

## 4. Out of Scope

- Integration with non-Docker container runtimes (Podman, containerd, etc.)
- Disk compaction for WSL v1 instances (VHDX does not apply)
- Cross-machine instance migration (network transfer)
- Linux GUI application (WSLg) management
