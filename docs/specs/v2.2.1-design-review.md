**Date**: 2026-03-22  
**Review Basis**: [v2.2.1-requirements.md](v2.2.1-requirements.md) + [v2.2.1-design.md](v2.2.1-design.md) + codebase inspection  
**Status**: Issues identified — design must be revised before implementation begins

---

## Summary

16 issues were found by cross-checking the design document against the live codebase. They are classified as:

- **BLOCKER** — Design describes code that cannot compile or will produce wrong runtime behaviour without correction.
- **GAP** — Feature described in requirements has no design coverage; will lead to missing implementation.
- **INACCURACY** — Design describes the codebase incorrectly; will mislead developers.
- **RISK** — Design is technically viable but carries elevated implementation risk that should be called out.

## Detailed Findings

---

### Issue 1 — BLOCKER: Watcher `Start()` placement creates a data-race

**Design §3.4** states:
> In `MainViewModel.InitializeAsync()`: `_wslEventWatcher.Start();`

**Actual startup sequence in `MainWindow.OnLoaded`**:
```
OnLoaded
  ├── await _viewModel.InitializeAsync()   ← design proposes Start() here
  └── _ = LoadDataInBackgroundAsync()      ← initial instance load happens here (fire-and-forget)
```

If `Start()` fires before the initial `LoadInstancesAsync` completes, a WMI event (e.g., a WSL process starting in the background) can trigger `OnCacheInvalidated` which calls `LoadInstancesAsync` concurrently with the first load. Two simultaneous `Instances.Clear()` + rebuild loops on different async continuations = observable list corruption.

**Required fix**: Call `_wslEventWatcher.Start()` at the **end** of `LoadDataInBackgroundAsync()`, after the initial instance list is loaded.

### Issue 2 — BLOCKER: `CompactInstanceAsync` (whatIf) cannot return reclaimable bytes

**Design §2.5.1 and §3.3.2** both describe reading the estimated reclaimable space from `whatIf`:
```csharp
whatIf = await IWslManagerService.CompactInstanceAsync(name, progress, whatIf: true, ct)
// then: show estimated reclaim
```

**Actual interface** (`IWslManagerService.cs`):
```csharp
Task CompactInstanceAsync(string instanceName,
    IProgress<(double Percentage, string Message)>? progress = null,
    bool whatIf = false,
    CancellationToken cancellationToken = default);
```

The return type is `Task` (void). The whatIf path cannot return a bytes-saved value. The `progress` callback passes `(double, string)` — the PS cmdlet likely sends a reclaimable-space string through `progress.Message`, but the design does not acknowledge this parsing requirement.

**Plus**: the after-size "result panel" (§2.5.1) shows `9.3 GB → saved 3.1 GB`. `DiskSize` on `WslInstance` is the VHDX physical file size and is not automatically updated after compaction. The design must specify:
1. Record `beforeSize = Instance.DiskSize` before calling the method.
2. Parse reclaimable estimate from the `progress` callback message in the whatIf phase (or read VHDX size manually via `GetInstanceDiskSizeAsync` before/after).
3. After compaction, call `GetInstanceDiskSizeAsync` again and compare to `beforeSize`.

### Issue 3 — BLOCKER: `IWslManagerService` has no `ShutdownAsync`

**Design §3.3.5** calls:
```csharp
await IWslManagerService.ShutdownAsync()
```

Searching `IWslManagerService.cs` — this method **does not exist**. The interface has `StopInstanceAsync(name)` only.

**Required fix**: Either add `Task ShutdownWslAsync(CancellationToken ct = default)` to `IWslManagerService` (which runs `wsl.exe --shutdown` via `IWslCliRunner`), or the design must describe using `IWslCliRunner.RunAsync("--shutdown")` directly in `WslConfigSectionViewModel`. The former is cleaner and testable.

### Issue 4 — BLOCKER: `ObservableCollection<T>` has no `.Filter` property

**Design §3.3.6** shows:
```csharp
Instances.Filter = inst => activeFilters.All(f => inst.Tags.Contains(f.Name))
```

`ObservableCollection<WslInstanceViewModel>` has no `Filter` property. WPF filtering is applied to the **view**, not the collection. The correct approach:

```csharp
// At MainViewModel construction:
_instancesView = CollectionViewSource.GetDefaultView(Instances);

// On filter change:
_instancesView.Filter = activeFilters.Any()
    ? o => activeFilters.All(f => ((WslInstanceViewModel)o).Tags.Contains(f.Name))
    : null;
_instancesView.Refresh();

// Group by tag:
_instancesView.GroupDescriptions.Clear();
if (IsGroupByTag)
    _instancesView.GroupDescriptions.Add(new PropertyGroupDescription("Tags[0]"));
```

The XAML `ItemsSource` must bind to `InstancesView` (the `ICollectionView` property), not `Instances`. Add `public ICollectionView InstancesView => _instancesView;` to `MainViewModel`.

**Note**: Grouping by tag is also non-trivial because one instance can have multiple tags. A flat single-tag group description only groups by the first tag. True multi-tag grouping requires a custom `IValueConverter` that flattens to multiple group rows or a separate `GroupedInstances` collection. The design should choose one approach explicitly.

### Issue 5 — GAP: `IBackupService` has no backup history method

**Design §2.5.5 and §3.8.1** describe a backup history list showing "timestamp, file size, status."

**`IBackupService` methods** (`IBackupService.cs`): `GetSchedulesAsync`, `SaveScheduleAsync`, `RemoveScheduleAsync`, `InvokeBackupAsync`. No history query method.

**`BackupSchedule` model**: has `Destination`, `Frequency`, `RetentionCount`, `Time`, `CreatedAt` — no `LastRun`, no history list.

Options to resolve:
- **A (preferred)**: Add `Task<List<BackupHistoryEntry>> GetBackupHistoryAsync(string instanceName, int limit = 10, CancellationToken ct = default)` to `IBackupService`. Implement by scanning the destination folder for TAR files matching `<instanceName>-*.tar`, sorted by creation time. A new `BackupHistoryEntry { DateTimeOffset Timestamp; long SizeBytes; string FilePath; bool IsLatest; }` model is needed.
- **B (simpler)**: `BackupTabViewModel` scans the `Destination` folder itself and doesn't go through a service. Acceptable if `IBackupService` stays thin.

The design must choose and document one of these. Currently neither is covered.

### Issue 6 — GAP: `WslConfig` has no unknown-key preservation mechanism

**Requirement E-01-8**: "Unknown INI keys not exposed in the UI must be preserved on save."

**`WslConfig` model** (`WslConfig.cs`):
```csharp
public class WslConfig
{
    public string? Memory { get; set; }
    public int? Processors { get; set; }
    public string? Swap { get; set; }
    public bool? LocalhostForwarding { get; set; }
    public string? NetworkingMode { get; set; }
}
```

There is no `Dictionary<string, string> UnknownKeys` or `List<string> PreservedLines` field. Whether `WslConfigService.SetWslConfigAsync` actually preserves unknown keys must be verified against its implementation. If not, the model needs a `Dictionary<string, string> RawExtras { get; set; }` property and the service must round-trip it.

**Action required**: Inspect `WslConfigService.SetWslConfigAsync` and document whether this is already handled. If not, add the model field and update the service.

### Issue 7 — GAP: Resources Tab — `GetInstanceConfigAsync` returns `object?`

**Design §2.5.2** says the Resources tab reads the current sparse mode state. The service to call is `IWslManagerService.GetInstanceConfigAsync(name)`.

**Interface signature**:
```csharp
Task<object?> GetInstanceConfigAsync(string name, CancellationToken cancellationToken = default);
```

Return type is `object?`. Looking at the implementation (`WslManagerService.cs` line 1484), it returns a PowerShell-parsed JSON object (a `Dictionary<string, JsonElement>` or similar). There is no strongly typed model.

**The design must specify**:
1. What concrete type `GetInstanceConfigAsync` returns (inspect the implementation to find out).
2. How `ResourcesTabViewModel` extracts the `SparseMode` flag from the returned object.
3. Or: add `Task<InstanceResourceConfig> GetInstanceResourceConfigAsync(string name, ct)` with a typed `InstanceResourceConfig { bool IsSparseMode; int WslVersion; }` model.

### Issue 8 — GAP: `ExportInstanceAsync` is `Task` — no progress data source

**Design §2.5.1 (Export flow)** says: "show progress (elapsed time + file size)."

**Interface**:
```csharp
Task ExportInstanceAsync(string name, string destination, bool force = false, CancellationToken cancellationToken = default);
```

Returns `Task` (void), no progress callback. There is no way to get in-flight file size or percentage.

**Design must specify one of**:
- **A**: Show only elapsed time (via `Stopwatch`) + an indeterminate `ProgressRing`. The "file size" in the progress label means the final file size shown in the completion dialog, read from disk after `ExportInstanceAsync` returns.
- **B**: Add `IProgress<(double, string)>?` parameter to `ExportInstanceAsync` and have the PS cmdlet emit progress events (larger change, out of scope for v2.2.1).

Option A is consistent with the requirements' `ProgressRing` (indeterminate) guidance and doesn't require a service change.

### Issue 9 — INACCURACY: Registry Phase 3 is already implemented inside `GetInstancesNativeAsync`

**Design §3.5** states:
> Complete Phase 3 (registry reads via `Microsoft.Win32.RegistryKey`): replace all remaining PS registry queries in `WslManagerService` with direct C# registry calls.

**Actual code** (`WslManagerService.cs` line 172):
```csharp
using var hive = Microsoft.Win32.RegistryKey.OpenBaseKey(
    Microsoft.Win32.RegistryHive.CurrentUser,
    Microsoft.Win32.RegistryView.Registry64);
```

Registry reads ARE already done with `Microsoft.Win32.RegistryKey` inside `GetInstancesNativeAsync`. The native path is Phase 1+2+3 combined. The `LxssRegistryPath = @"HKCU:\Software\..."` constant at line 23 is a **PS-style path string used only for the PS fallback path** — not a leftover.

**Actual Phase 3 verification scope**: Check which methods in `WslManagerService` still fall through to `_powerShellService` for registry access, rather than re-doing registry work that's already done. The design's proposed `IRegistryReader` abstraction is **not needed** — `Microsoft.Win32` APIs are already in use. Remove that proposal from the design doc.

### Issue 10 — INACCURACY: `OnCacheInvalidated` already exists; `IsAutoRefreshing` is the only missing piece

**Design §3.4** implies `OnCacheInvalidated` needs to be written. It already exists:

```csharp
// MainViewModel.cs line 359
private void OnCacheInvalidated(object? sender, EventArgs e)
{
    _ = Application.Current.Dispatcher.InvokeAsync(
        async () => await LoadInstancesAsync(CancellationToken.None));
}
```

What is actually missing:
1. `_wslEventWatcher.Start()` is never called (confirmed by grepping the whole Desktop project — zero results for `.Start()`).
2. `IsAutoRefreshing` property and the toolbar spinner do not exist.

The design §3.4 code sample showing `IsAutoRefreshing = true/false` is the correct enhancement — but the handler must be updated, not written from scratch.

**Also note**: the existing handler uses `Application.Current.Dispatcher.InvokeAsync(async () => ...)` which is fire-and-forget from the perspective of the Dispatcher callback. Setting `IsAutoRefreshing = false` after `LoadInstancesAsync` completes requires `await` inside the lambda, which already works with `InvokeAsync(async ...)`. The design is sound; just clarify it's a modification not a new method.

### Issue 11 — INACCURACY: Design references `_dialogService.ShowErrorAsync` which does not exist

**Design §3.6.2** shows:
```csharp
await _dialogService.ShowErrorAsync(MainViewModel.FormatAlertMessage(ex));
```

There is no `IDialogService` or `_dialogService` in the codebase. The existing pattern in every ViewModel is:
```csharp
await ShowAlert(Properties.Resources.ErrorTitle, MainViewModel.FormatAlertMessage(ex));
```
where `ShowAlert` is a private method constructing `Wpf.Ui.Controls.MessageBox` inline.

**Options**:
- **A (status quo)**: Each VM has its own `private async Task ShowErrorAsync(string msg)` helper. Simple, but violates DRY and makes dialog testing harder.
- **B (extract)**: Introduce `IDialogService` with `ShowErrorAsync` as part of this release — acceptable if it's scoped to v2.2.1. Requires DI registration.

The design must pick one and be consistent. Currently it proposes B but without any design for the `IDialogService` interface, its DI registration, or its implementation. If B is chosen, add it to the new components list in §3.1.

### Issue 12 — INACCURACY: `WslInstanceViewModel` lives in `MainViewModel.cs`

**Design §3.1 and §3.2** reference `WslInstanceViewModel` as if it were a standalone class and add `OpenDetailsCommand` and other new members to it.

**Reality**: `WslInstanceViewModel` is declared as a second `partial class` at line 573 of `MainViewModel.cs` in the same file. It currently has 400+ lines. Adding `IsSelected`, `Tags`, `DockerIntegrationEnabled`, and `OpenDetailsCommand` will make this file unmanageable.

**Design should specify**: Move `WslInstanceViewModel` to `ViewModels/WslInstanceViewModel.cs` before adding new members to it. This is a pre-condition for Phase 1 work (§4), not an optional refactor.

### Issue 13 — RISK: `BackupSchedule.Frequency` is a single encoded string

**`BackupSchedule` model**:
```csharp
public string Frequency { get; set; } = "Daily";
// Valid values: "Daily" | "Weekly:Monday" | "Monthly:1"
```

**Design §2.5.5** shows separate UI controls: `[Daily ▾]` dropdown + day-of-week picker (for Weekly) + day-of-month picker (for Monthly).

`BackupTabViewModel` must:
1. On load: parse `"Weekly:Monday"` → set `FrequencyType = "Weekly"`, `DayOfWeek = "Monday"`.
2. On save: re-combine `FrequencyType + ":" + DayOfWeek` → `"Weekly:Monday"`.

This parsing logic is not trivial and not mentioned in the design. Add a `FrequencyParser` helper or specify the mapping in the design explicitly to avoid each developer re-inventing it differently.

### Issue 14 — RISK: Service-locator anti-pattern will worsen with new tab services

**Current `LoadInstancesAsync`** (line 216):
```csharp
var tagService = _serviceProvider.GetRequiredService<ITagService>();
var backupService = _serviceProvider.GetRequiredService<IBackupService>();
var vm = new WslInstanceViewModel(instance, ..., tagService, backupService);
```

This service-locator pattern is already a known smell. Adding `IDockerIntegrationService` for the instance card indicator (C-01-8) and other services will make the loop wider.

**Design should specify**: Inject `ITagService`, `IBackupService`, and `IDockerIntegrationService` as constructor parameters on `MainViewModel`, store them as fields, and pass them into `WslInstanceViewModel`. The `_serviceProvider` in the loop should be avoided for known service types. (The `_serviceProvider` is still needed for page navigation objects — that is fine.)

### Issue 15 — RISK: `WslOperationTimeoutException` hardcodes `UnknownError`

**Requirement F-03-1**: "All `throw` sites in `DistroNexus.Core` services must use a non-`UnknownError` code."

**`WslOperationTimeoutException.cs`** (lines 23, 36, 50):
```csharp
: base($"...", DistroNexusErrorCode.UnknownError, ...)
```

All three constructors hardcode `DistroNexusErrorCode.UnknownError`. If E-09 rollout (F-03-1) is enforced literally, `WslOperationTimeoutException` itself fails the requirement. The design §3.6.1 lists the services to audit but doesn't mention fixing the exception constructors.

**Action**: Either add a `TimeoutError` code to `DistroNexusErrorCode`, or allow `WslOperationTimeoutException` to accept a code parameter. Document this explicitly in the error code rollout design.

---

### Issue 16 — RISK: Proposed `IRegistryReader` interface is unnecessary overhead

**Design §3.5** proposes:
> Add `IRegistryReader` (new interface abstracting `Registry.CurrentUser`) — no test should spawn a real PowerShell process.

`Microsoft.Win32.Registry` is not mockable via an interface in standard xUnit. However, `GetInstancesNativeAsync` already uses a direct registry call. The practical unit-testing approach for F-02 is:

- Mock `IWslCliRunner` (already an interface) — covers parsing logic.
- Use integration tests for registry reads (they are pure reads, no state mutation).
- Or wrap only the registry reads in a thin `IRegistryAccess` — acceptable, but the design should justify the cost.

Given that `WslManagerService` is already 1500+ lines and Phase 3 registry reads are essentially done, the IRegistryReader proposal adds interface/implementation/DI overhead for marginal test benefit. The design should either (a) justify it with a concrete test scenario that can only be covered with the abstraction, or (b) drop it and note that Phase 3 is already complete for the native path.
