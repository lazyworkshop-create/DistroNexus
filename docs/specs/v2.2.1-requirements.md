# DistroNexus v2.2.1 Requirements Specification

**Version**: 2.2.1
**Date**: 2026-03-22
**Status**: Draft
**Branch**: feat/v2.2.1

---

## 1. Release Goal

v2.2.1 is a **completion release** for v2.2.0. Its sole purpose is to close every unfinished v2.2.0 commitment: wiring the already-built Core service capabilities into the desktop GUI, completing partial implementations, and finishing non-UI infrastructure work that was promised but not delivered.

No new product direction is introduced. The release is done when every item originally committed in v2.2.0 either has a shipped desktop surface or a documented non-UI completion path.

---

## 2. Scope Statement

v2.2.1 covers:

- Desktop UI exposure for all v2.2.0 backend capabilities that lack a GUI entry point
- Completion of partially implemented features (E-07, E-09)
- Completion of infrastructure work still outstanding from v2.2.0 (E-08)
- Validation that the full acceptance criteria from v2.2.0 can now be met end-to-end

v2.2.1 does **not** cover:

- Any feature, capability, or scope item not already present in v2.2.0
- Redesign of the application beyond what is necessary to expose v2.2.0 functionality

## 4. UX and Behavior Conventions

These conventions apply to all UI work in v2.2.1 and take precedence over per-feature descriptions where they conflict.

| ID | Convention |
|----|------------|
| UX-01 | Any operation that calls a backend service must set `IsBusy = true` on the relevant `WslInstanceViewModel` for the duration, blocking all other operations on that instance |
| UX-02 | Operations with duration > ~1 s must show a progress indicator; use `ProgressRing` (indeterminate) or a phase-text label for long operations where percentage is not computable |
| UX-03 | All destructive or irreversible operations (remove, compact, export-overwrite, disable Docker) must show a `ConfirmDialog` before proceeding |
| UX-04 | After a successful operation that changes instance state, immediately call `RefreshCommand` or equivalent to update the dashboard |
| UX-05 | All error dialogs must use `MainViewModel.FormatAlertMessage(ex)` to prefix the error code (e.g., `[DN-1001]`) when a `WslException` or `WslOperationException` is available |
| UX-06 | All controls that apply only to WSL v2 instances must be hidden or disabled for WSL v1 instances with a tooltip explaining why |
| UX-07 | All new UI text (labels, tooltips, button content, dialog messages) must have a corresponding entry in `Properties/Resources.resx`; no hard-coded strings in XAML or ViewModels |
| UX-08 | Features that depend on a running instance (port list, Docker toggle, terminal actions) must show a placeholder message when the instance is stopped |
| UX-09 | Features that depend on optional system software (Docker Desktop, Hyper-V, Task Scheduler) must degrade gracefully: grey out the relevant control and provide a tooltip explaining the missing dependency |

## 5. Desktop Shell Completion (Group A)

### Background

The current `MainWindow.xaml` dashboard is a card list with per-instance actions (Start/Stop/Terminal) and a `MoreButton` flyout (Move/Rename/SetCredentials/ForceRefresh/Remove). There is no instance detail panel or tab surface. Several v2.2.0 features assume richer per-instance views.

### Shell Pattern Decision

v2.2.1 adopts the following pattern for exposing new per-instance functionality:

1. **More menu expansion** — high-frequency single-action items (Compact Disk, Export Instance) are added directly to the existing `MoreButton` `ContextMenu`.
2. **Instance Detail Dialog** — a new modal tabbed dialog (`InstanceDetailDialog`) is introduced for multi-section views. Tabs: **Disk**, **Resources**, **Integrations**, **Network**, **Backup**. Opened via a new **Details** button or menu item on each instance card.
3. **Settings page extension** — items that are global rather than per-instance (`.wslconfig` editor, Manage Tags) are added as new collapsible panels on the existing `SettingsPage`.
4. **Dashboard list enhancements** — tag chips and the tag filter bar live in the dashboard, above and alongside the existing card list.

### Detailed Requirements

| ID | Requirement |
|----|-------------|
| A-01 | Add a **Details** entry to the existing `MoreButton` `ContextMenu` on each instance card; this opens `InstanceDetailDialog` for that instance |
| A-02 | `InstanceDetailDialog` is a `Window` (or `ui:FluentWindow`) sized ~780 × 540 (resizable), with a `TabControl` containing: Disk, Resources, Integrations, Network, Backup tabs |
| A-03 | Each tab is implemented as a separate `UserControl` and corresponding `ViewModel` (e.g., `DiskTabViewModel`, `NetworkTabViewModel`) to keep concerns isolated |
| A-04 | The dialog receives the target `WslInstanceViewModel` on construction and shares the same instance busy-state (`IsBusy`) |
| A-05 | Add a **multi-select mode** toggle to the dashboard toolbar (checkbox or toggle button); when active, instance cards show a checkbox and the **Compact Selected** bulk action button appears |
| A-06 | The multi-select model is limited to bulk disk compaction (F-01-8) in v2.2.1; other bulk actions are out of scope |
| A-07 | All new XAML UserControls and dialogs must apply `WindowBackdropType="Mica"` and use `{DynamicResource}` for all color/brush references to support theme switching |

## 11. Delivery Sequencing

The following order is recommended to minimise integration risk:

| Phase | Work | Rationale |
|-------|------|-----------|
| 1 | Group A — Desktop shell (InstanceDetailDialog skeleton, multi-select model) | All feature groups B–D depend on the dialog shell existing |
| 2 | Group B — Instance operations (compact, export/import, sparse mode) | High user value; all backed by `IWslManagerService` which is already tested |
| 3 | Group E — Settings additions (.wslconfig editor, Manage Tags) | Isolated to SettingsPage; low coupling to instance dialog work |
| 4 | Group C — Integrations and diagnostics (Docker, Network tab) | Depend on instance dialog tabs being available from Phase 1 |
| 5 | Group D — Backup scheduling (Backup tab) | Depends on instance dialog; slightly more complex UX |
| 6 | Group E — Dashboard tag UI (filter bar, group view, tag chips) | Depends on TagService being exercised; can proceed in parallel with Phase 4–5 |
| 7 | Group F — Platform quality (E-07 watcher startup, E-08 Phase 3, E-09 uniform rollout) | Can proceed in parallel throughout; must be complete before release |

## 12. Release Exit Criteria

v2.2.1 is complete when **all** of the following are true:

1. Every item in the v2.2.0 Gap Summary table (Section 3) has a shipped desktop surface or a documented non-UI completion path
2. No backend-only feature that was promised as GUI-visible in v2.2.0 remains without a desktop entry point
3. All acceptance criteria in Sections 6–10 are met
4. All new ViewModels and dialogs have unit tests covering the primary success path and the principal error path
5. All new UI strings are present in `Properties/Resources.resx` (both `en-US` and `zh-CN`)
6. `error-codes.md` is complete and up to date
7. The existing Pester test suite passes without regression
8. Manual walkthrough of every feature in Sections 6–10 completes without error on a clean Windows 11 machine with WSL 2 installed

---

## 13. Out of Scope

- Any feature or capability not already present in v2.2.0
- Integration with non-Docker container runtimes (Podman, containerd, etc.)
- Disk compaction for WSL v1 instances
- Cross-machine instance migration
- Linux GUI application (WSLg) management
- Redesign of any existing UI beyond what is necessary to expose v2.2.0 functionality

## 15. Risks

| Risk | Impact | Mitigation |
|------|--------|------------|
| Shell redesign complexity — `InstanceDetailDialog` is a non-trivial new surface | High | Build skeleton first (Group A Phase 1); validate UX pattern before filling tabs |
| Multi-select model not yet designed or built | Medium | Scope multi-select strictly to bulk compaction in v2.2.1; revisit general multi-select for v2.3 |
| Backend availability ≠ feature complete | Medium | Each feature group's acceptance criteria explicitly tests edge states (stopped instance, WSL v1, missing dependency) |
| Persisted-file write conflicts (Docker settings, .wslconfig, backup JSON) | Medium | Define conflict handling per feature section; test with Docker Desktop running |
| Version/permission variability (WSL version, admin rights, Docker absent) | Medium | UX-06, UX-09 conventions handle degraded states; test matrix must cover them |
| Localization completeness | Low–Medium | UX-07 requires resource strings for all new text before merge |
