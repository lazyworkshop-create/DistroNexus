# DistroNexus v2.3.0 Requirements Specification

**Version**: 2.3.0  
**Date**: 2026-07-11  
**Status**: Draft  
**Branch**: `feature/2.3.0`

---

## 1. Release Vision

DistroNexus v2.3.0 evolves the product from a WSL distribution manager into a Windows-native **WSL development environment control center**.

The release must preserve the instance lifecycle, storage, backup, template, Docker, networking, and automation capabilities completed in v2.2.1 while adding an integrated operational layer for health diagnostics, configuration, recovery, devices, monitoring, project workflows, Linux GUI applications, container runtimes, and trusted templates.

The release is intentionally broad. To keep delivery measurable, every feature group has an independent completion gate, and the overall release uses the phased plan in Section 18. A feature must not be presented as available until its gate is met.

---

## 2. Goals

1. Detect common WSL host and distribution problems and provide safe, explainable remediation.
2. Manage global `.wslconfig` and per-distribution `/etc/wsl.conf` settings without requiring manual file editing.
3. Provide practical systemd service administration from Windows.
4. Make advanced WSL networking understandable and diagnosable.
5. Turn existing export and backup primitives into recovery-point and cloning workflows.
6. Support developer hardware workflows through `usbipd-win`.
7. Show useful per-instance resource, process, storage, and network telemetry.
8. Let users launch a complete development workspace rather than a collection of unrelated tools.
9. Provide discoverable WSLg application launch and troubleshooting.
10. Extend container integration beyond Docker Desktop, beginning with Podman.
11. Establish a safe, extensible template marketplace and trust model.
12. Expose automatable equivalents for new capabilities where security and platform APIs permit.

---

## 3. Non-Goals

- Replacing Windows Terminal with a built-in terminal emulator.
- Building a general-purpose Linux file manager.
- Building a Kubernetes cluster administration console.
- Providing a general AI assistant.
- Synchronizing complete WSL instances through a DistroNexus-hosted cloud service.
- Claiming instant or incremental filesystem snapshots when the implementation uses full TAR or VHDX exports.
- Silently elevating privileges, installing optional dependencies, or changing security-sensitive configuration.
- Supporting remote Linux hosts unrelated to the local WSL installation.
- Guaranteeing identical capability on unsupported Windows or WSL versions.

## 4. Product and UX Conventions

| ID | Requirement |
|---|---|
| UX-01 | Every host- or instance-level feature must query capability support before enabling its controls. |
| UX-02 | Unsupported capabilities must show the unmet prerequisite and a safe next action. |
| UX-03 | Operations longer than one second must show progress and support cancellation when the underlying operation is cancellable. |
| UX-04 | Destructive, disruptive, privileged, or security-sensitive operations must show a confirmation summarizing impact. |
| UX-05 | Actions that restart or shut down WSL must list the affected running instances. |
| UX-06 | New UI text must be localized through application resources in English and Simplified Chinese. |
| UX-07 | Errors must use structured DistroNexus error codes and include a copyable diagnostic detail view. |
| UX-08 | Passwords, access tokens, and private keys must never be written to application logs. |
| UX-09 | Optional software must not be installed without explicit user confirmation. |
| UX-10 | Feature pages must distinguish current state, desired state, and pending-restart state. |
| UX-11 | Changes to configuration files must preserve unknown keys, comments, and unrelated sections whenever practical. |
| UX-12 | Every remediation action must explain what it will change and whether it can be undone. |

## 5. Platform Capability Detection (Foundation A)

### 5.1 Purpose

Introduce a single capability service so views and services do not duplicate Windows build, WSL version, kernel version, distribution version, elevation, and optional dependency checks.

### 5.2 Functional Requirements

| ID | Requirement |
|---|---|
| A-01 | Add an `IPlatformCapabilityService` in Core with a typed capability result model. |
| A-02 | Detect Windows edition, build, architecture, and whether the application is elevated. |
| A-03 | Detect WSL installation source, WSL version, kernel version, WSLg version, and update availability where the CLI exposes it. |
| A-04 | Detect per-instance WSL version, distribution identity, systemd availability, and systemd running state. |
| A-05 | Detect support for sparse VHD, mirrored networking, VHD export, import-in-place, systemd, WSLg, GPU compute, and USB/IP integration. |
| A-06 | Detect optional dependencies including Windows Terminal, VS Code, Docker Desktop, Podman, `usbipd-win`, and Windows Task Scheduler. |
| A-07 | Return `Supported`, `Unsupported`, `Unavailable`, `RequiresUpdate`, `RequiresElevation`, or `Unknown`, plus a localized reason. |
| A-08 | Cache stable host capabilities, invalidate them after WSL update or relevant settings changes, and refresh volatile instance capabilities on demand. |
| A-09 | Never infer support solely from Windows build when an authoritative CLI capability check is available. |

### 5.3 Acceptance Criteria

1. All new feature groups use the capability service before enabling actions.
2. Unit tests cover supported, outdated, absent, permission-denied, and malformed CLI output cases.
3. A missing optional dependency never prevents unrelated DistroNexus features from loading.

## 6. Health Center and Guided Repair (Feature B)

### 6.1 User Experience

Add a top-level **Health** page with host checks, per-instance checks, severity filters, last-run time, and a user-triggered rescan. Findings use `Healthy`, `Information`, `Warning`, or `Critical` severity.

### 6.2 Checks

| ID | Requirement |
|---|---|
| B-01 | Check Windows and WSL prerequisites, WSL version, kernel version, WSLg version, and pending WSL updates. |
| B-02 | Check required Windows optional features and virtualization availability. |
| B-03 | Parse `.wslconfig` and report invalid, obsolete, conflicting, or unsupported values. |
| B-04 | Parse `/etc/wsl.conf` per instance and report invalid or unsupported settings. |
| B-05 | Report host disk pressure, VHDX size, Linux filesystem usage, and likely reclaimable space. |
| B-06 | Detect DNS resolution, Windows-to-WSL connectivity, WSL-to-Windows connectivity, localhost forwarding, proxy, and common VPN/mirrored-network issues. |
| B-07 | Report failed systemd units and abnormal distribution startup. |
| B-08 | Check optional integrations and explain unavailable Docker, Podman, USB, WSLg, terminal, and editor features. |
| B-09 | Detect backup schedules with repeated failures, missing destinations, or inadequate free space. |
| B-10 | Detect templates whose recorded installation state no longer satisfies their declared health checks. |

### 6.3 Repair and Reporting

| ID | Requirement |
|---|---|
| B-11 | Safe findings may expose a one-click repair; disruptive findings must require confirmation. |
| B-12 | Supported repairs include updating WSL, correcting known configuration values, restarting WSL, enabling required Windows features through an explicit elevated flow, trimming filesystems, and opening the relevant settings page. |
| B-13 | Configuration repairs must create a timestamped local backup before writing. |
| B-14 | Repairs must show changed files/commands and their results. |
| B-15 | Generate a redacted diagnostic report in Markdown or JSON containing versions, capability states, findings, recent structured errors, and user-selected logs. |
| B-16 | Diagnostic export must preview included data and exclude usernames and paths when redaction is enabled. |

### 6.4 Acceptance Criteria

1. A healthy supported machine completes a scan without false critical findings.
2. DNS failure, invalid configuration, low disk space, outdated WSL, and failed systemd service fixtures produce the expected findings.
3. Every automatic repair is idempotent or clearly marked non-idempotent.
4. A repair failure leaves configuration recoverable from its backup.

## 7. Global and Per-Distribution Configuration (Feature C)

### 7.1 Global `.wslconfig`

Extend the existing editor to support:

- `memory`, `processors`, `swap`, `swapFile`, `pageReporting`
- `localhostForwarding`, `networkingMode`, `dnsTunneling`, `firewall`, `autoProxy`
- `hostAddressLoopback`, `ignoredPorts`, `bestEffortDnsParsing`, and proxy timeout settings when supported
- custom kernel and kernel command line
- nested virtualization and supported experimental keys

### 7.2 Per-Distribution `/etc/wsl.conf`

| ID | Requirement |
|---|---|
| C-01 | Add an instance **Configuration** tab that reads and edits `/etc/wsl.conf`. |
| C-02 | Manage boot command and systemd enablement. |
| C-03 | Manage default user. |
| C-04 | Manage automount root, options, enabled state, fstab processing, metadata, umask, and case sensitivity settings supported by WSL. |
| C-05 | Manage Windows interoperability and Windows PATH injection. |
| C-06 | Manage hostname and supported generated network file settings. |
| C-07 | Preserve unknown sections and keys and offer a raw read-only preview before saving. |
| C-08 | Validate values before write and report line-level parse errors. |
| C-09 | Indicate whether instance termination or full `wsl --shutdown` is required. |
| C-10 | Create a backup in the distribution before updating the file. |

### 7.3 Acceptance Criteria

1. Round-tripping a file with comments and unknown keys does not remove them.
2. Invalid values cannot be saved through the form.
3. Enabling systemd followed by an approved restart results in systemd running on a supported distribution.
4. Settings unavailable on the detected WSL version are disabled with an explanation.

## 10. Recovery Points, Clone, and Restore (Feature F)

### 10.1 Terminology

The UI must use **Recovery Point** unless the underlying method provides genuine snapshot semantics. TAR and VHDX exports must not be described as incremental snapshots.

### 10.2 Functional Requirements

| ID | Requirement |
|---|---|
| F-01 | Create named recovery points with description, tags, timestamp, source instance, WSL version, format, size, checksum, and application version metadata. |
| F-02 | Support TAR and, for WSL 2, VHDX export formats. |
| F-03 | Verify free destination space before export and calculate a checksum after completion. |
| F-04 | Restore to a new instance name and location without overwriting an existing instance. |
| F-05 | Clone an instance through export/import or VHDX import-in-place when supported and safe. |
| F-06 | Offer a pre-operation recovery point before template application, major configuration changes, WSL version conversion, or destructive repair. |
| F-07 | Allow recovery point verification, notes editing, deletion, retention policies, and reveal-in-Explorer. |
| F-08 | Clearly indicate whether a consistent export requires stopping the instance and offer restart afterward. |
| F-09 | Preserve existing scheduled backup functionality and display scheduled backups and manual recovery points in a unified history with type filters. |
| F-10 | Never delete the only known recovery point as an implicit side effect. |

### Acceptance Criteria

1. A TAR recovery point restores to a bootable, distinct instance.
2. A supported VHDX recovery point can be imported or registered in place.
3. Checksum failure blocks restoration by default.
4. Cancellation and disk-full failures do not leave a registered partial instance.

## 13. Development Workspaces (Feature I)

### 13.1 Workspace Model

A workspace binds a WSL instance, Linux working directory, optional Windows path, launch actions, health checks, and user-selected tools.

| ID | Requirement |
|---|---|
| I-01 | Create, edit, duplicate, remove, import, and export workspace definitions. |
| I-02 | Bind a workspace to an existing instance or define a missing-instance remediation. |
| I-03 | Configure launch actions for Windows Terminal, VS Code Remote WSL, File Explorer, browser URLs, arbitrary approved Linux commands, systemd services, and Docker Compose/Podman Compose. |
| I-04 | Let users order actions and choose sequential or parallel execution where safe. |
| I-05 | Run preflight checks for instance state, directory, tools, services, ports, and optional template prerequisites. |
| I-06 | Display launch progress and allow retry of an individual failed action. |
| I-07 | Support Start Menu or desktop shortcuts using a stable workspace identifier. |
| I-08 | On workspace close, optionally stop user-selected services or terminate the instance; never do so by default. |
| I-09 | Store definitions under `%APPDATA%\DistroNexus` with a documented versioned schema. |
| I-10 | Treat arbitrary commands as trusted local user configuration and show them in full before first execution or imported execution. |

### Acceptance Criteria

1. A workspace can start an instance, open its project in Windows Terminal and VS Code, start a service, and open a local URL.
2. Missing VS Code, missing path, busy port, and failed service cases identify the failed action.
3. Imported definitions containing commands require explicit trust before commands run.

| ID | Requirement |
|---|---|

## 17. Automation, Security, Data, and Quality

### 17.1 PowerShell and Automation

- Add PowerShell commands for health scans, capability queries, recovery points, workspace launch, systemd operations, and USB listing where practical.
- Commands must support `-WhatIf` and `-Confirm` for changing operations when PowerShell semantics permit.
- JSON output models must be versioned and stable enough for automation.
- UI and PowerShell must call shared Core services rather than maintaining separate business logic.

### 17.2 Security Requirements

| ID | Requirement |
|---|---|
| SEC-01 | Validate instance names, Windows paths, Linux paths, bus IDs, unit names, ports, URLs, and executable arguments at trust boundaries. |
| SEC-02 | Invoke commands using structured argument lists; do not construct shell commands from unescaped user input. |
| SEC-03 | Centralize privileged Windows operations behind a minimal elevated helper or explicit process boundary. |
| SEC-04 | Never store Linux sudo passwords or Windows credentials. |
| SEC-05 | Redact secrets and identifying paths from logs and exported reports according to user-selected redaction. |
| SEC-06 | Back up modified configuration and use atomic replacement where supported. |
| SEC-07 | Treat marketplace scripts, workspace commands, and desktop entry commands as untrusted input. |
| SEC-08 | Document the security boundary and limitations of USB attachment, container sockets, Windows interoperability, and templates. |

### 17.3 Persistence

New persisted formats must be versioned and stored under `%APPDATA%\DistroNexus` unless they are instance-local. Migrations must be idempotent, retain a backup, and tolerate a newer unknown schema by falling back to read-only behavior rather than overwriting it.

### 17.4 Testing

- Unit tests for parsers, capability matrices, validation, state transitions, and command argument construction.
- Integration tests for shared Core services using recorded CLI fixtures when WSL is unavailable.
- Opt-in WSL 2 integration tests for systemd, networking, recovery, monitoring, WSLg discovery, Podman, and USB.
- UI tests for supported, unsupported, stopped, busy, permission-denied, and dependency-missing states.
- Security tests for command injection, malicious template manifests, desktop entries, workspace imports, path traversal, and log redaction.
- Manual compatibility matrix across supported Windows builds, x64/ARM64, current Store WSL, WSL 1 degradation, and representative Ubuntu/Debian distributions.

## 18. Delivery Plan and Release Gates

The following phases are part of the v2.3.0 scope. They may be developed and previewed independently, but a feature group is complete only when its acceptance criteria, localization, documentation, and tests are complete.

| Phase | Feature Groups | Gate |
|---|---|---|
| 1 | A Capability Detection | Required before all other groups merge to release branch. |
| 2 | B Health Center, C Configuration, D systemd, E Networking | Core control-center experience complete. |
| 3 | F Recovery Points, H Monitoring | Operational safety and observability complete. |
| 4 | G USB, I Workspaces | Developer workflow integration complete. |
| 5 | J WSLg, K Container Runtimes | Extended integration surfaces complete. |
| 6 | L Template Marketplace | Trust, source, update, and rollback model complete. |
| 7 | Automation, security review, localization, docs, compatibility | Release candidate gate. |

### 18.1 Release-Candidate Gate

v2.3.0 may be declared release candidate only when:

1. No enabled UI action bypasses capability detection.
2. All high-impact operations have confirmation, progress, cancellation where possible, and structured errors.
3. English and Simplified Chinese resources and user documentation cover every shipped feature.
4. Relevant non-WSL unit tests and builds pass.
5. Opt-in WSL tests pass on the documented reference environment, or deviations are explicitly documented and approved.
6. Security review finds no unresolved critical or high-severity issue.
7. Upgrade from v2.2.1 preserves settings, tags, templates, backups, and instance registrations.
8. Disabled or unavailable optional integrations do not regress core instance management.

## 20. Risks and Mitigations

| Risk | Impact | Mitigation |
|---|---|---|
| Scope is too large for one release | High | Independent feature gates, phased previews, and no partial feature advertised as complete. |
| WSL CLI output or features vary by version | High | Capability detection, structured parsers with fixtures, and graceful degradation. |
| Privileged operations broaden attack surface | High | Minimal elevated boundary, validation, exact previews, and security tests. |
| Template or workspace execution runs untrusted code | High | Trust prompts, capability declarations, script review, checksums/signatures, and recovery points. |
| Monitoring creates performance overhead | Medium | Visible-tab polling, configurable intervals, cancellation, and bounded history. |
| VHDX recovery consumes significant disk space | Medium | Preflight free-space checks, estimates, retention, checksums, and cancellation cleanup. |
| USB semantics are confusing across distributions | Medium | Explicit VM-wide visibility explanation and state verification. |
| Configuration writes remove unknown settings | High | Round-trip preservation tests, backup, preview, and atomic writes. |
| Optional tools change their CLI or configuration | Medium | Adapter interfaces, version detection, fixture tests, and isolated failures. |

---

## 21. Success Measures

The release should be evaluated using opt-in, privacy-preserving project metrics or structured manual testing rather than mandatory telemetry:

- A user can identify and resolve a representative WSL configuration or network problem without opening a shell.
- A user can enable systemd and manage a service with clear restart and privilege behavior.
- A user can create, verify, clone, and restore a recovery point without orphaning a partial instance.
- A hardware developer can attach and verify a supported USB device through the UI.
- A user can launch a saved development workspace and understand any failed launch action.
- Unsupported platform and missing-dependency paths remain usable and explain next steps.
- Existing v2.2.1 instance, backup, template, Docker, and configuration workflows do not regress.

## Scope

Goals are listed in Section 2, exclusions in Section 3, feature requirements in Sections 4–17, delivery gates in Section 18, and documentation obligations in Section 19. This section provides the standard AgentTeam delivery index without changing that scope.

## Functional Requirements

### FR-001 Deliver the v2.3.0 WSL development environment control center
